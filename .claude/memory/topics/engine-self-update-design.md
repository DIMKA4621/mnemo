# Самооновлення рушія mnemo — дизайн (ще не заплановано у фазах)

**Статус: ідея, узгоджена з користувачем у розмові 2026-08-20, поза
`Memory-implementation-v3.md` фазами 0–7.** Перш ніж кодити — треба завести
рішення в `Memory-design-v3.md` §13 і, якщо релевантно, контракти. Нічого з
цього ще не реалізовано. Повний план (контракти, впорядковані кроки по
власниках модулів, ризики) вивів `planner`-агент 2026-08-20 — сам план не
записаний окремим файлом, підсумок і рішення по ризиках — нижче й у логах.

## Рішення по ризиках, піднятих планом

- **Міграція старої пласкої розкладки (`USER_HOME/src` + `USER_HOME/.venv`)
  на `versions/<tag>/{src,.venv}` + `current` — НЕ автоматизується.** Це
  єдина відома машина з рушієм (користувача), проєкт більше ніде не стоїть.
  Перехід на нову розкладку — **разова ручна дія** під час реалізації (просто
  перекласти наявний бекенд у правильну версійну теку й перезапустити), а не
  логіка виявлення/міграції старого layout всередині `install.ps1`/`.sh`.
  Якщо колись з'явиться друга машина з рушієм до цього переходу — рішення
  треба переглянути.
- **Перевірка цілісності завантаженого архіву — без SHA-звірки.** GitHub
  Releases API не дає checksum авто-архіву тегу за токеном, такого готового
  механізму немає. Рішення: **покластись на TLS**, прибрати фразу «звіряє
  SHA з release API» з дизайну апдейту. Секцію нижче «Механіка застосування»
  виправлено відповідно.

## Що оновлюється

**Тільки сам рушій** (`~/.claude/mnemo/`, спільний на всю машину). Проєкти,
підключені через `init`, цей процес не чіпає — вони лише клієнти рушія.

## Тригер

**Теги/релізи GitHub, не кожен коміт у master.** Свідомо, а не HEAD гілки:
WIP-коміти чи зламаний CI не мають розкочуватись самі. Перевірка —
`GET /repos/<owner>/mnemo/releases/latest` (публічний репо, без токена,
запас ліміту величезний навіть при перевірці раз на кілька годин).

## Автономність — напівавтоматика

- **Перевірка** — на бекенді, за таймером (кілька годин) + ручна кнопка
  «Перевірити зараз» у Налаштуваннях (той самий патерн, що вже є для
  hosted-endpoint probe).
- **Застосування** — тільки по явному кліку людини. Ніякого автозапуску
  апдейту без підтвердження.

## UX-флоу (продиктовано користувачем)

1. Плашка знизу-зліва (там, де зараз показується версія/машинний блок
   сайдбару): «Доступна нова версія».
2. Клік → модалка **по центру екрана**, темніший бекдроп (patterns, які вже є
   в консолі — не новий візуальний словник). Текст: яка версія, і
   попередження, що сервер буде зупинено й перезапущено. Кнопки OK/Відміна.
3. Клік OK — **дію більше не можна скасувати**. Одразу з'являється прогрес:
   завантаження з GitHub → установка пакетів → версіонування → запуск.
   Фронтенд показує ці кроки як події, без можливості щось натиснути, поки
   не завершиться (успіхом чи відкатом).
4. Бекенд **не блокується** під час завантаження й побудови venv — стара
   версія й далі обслуговує запити. Простій = лише сам момент
   `stop → перемикання → start`, а не весь процес підготовки.
5. Якщо після рестарту health не відповів — автоматичний відкат на
   попередню версію, і повідомлення користувачу «проблема, відкотили назад»
   замість мовчазної відмови чи мертвого сервісу.

### Пастка, яку ще треба вирішити технічно

Прогрес-канал (WebSocket) **не переживе** сам момент рестарту — це той самий
процес, який його обслуговує. Фронтенд має інтерпретувати обрив з'єднання
рівно в цю мить як «ще працює», а не як помилку, і дізнаватись фінальний
результат після реконекту / через `/api/update/status` — а не через
безперервний потік подій, який фізично не може лишатись безперервним.

## Версіонування на диску

- `~/.claude/mnemo/versions/<tag>/` — код + **власний venv** на кожну
  версію. `model-cache/` і `state/` лишаються спільні й поза версіями (модель
  — 2.2 ГБ, дублювати на кожну версію безглуздо).
- `~/.claude/mnemo/current` — **junction** (Windows `mklink /J`, без
  адмінки) на активну версію. Перемикання версії = атомарне перепризначення
  junction, а не копіювання файлів.
- Retention: тримати останні **3** версії; старіші видаляти, але тільки
  **після** підтвердженого успішного перемикання на новішу (щоб не знищити
  єдину robочу ціль відкату одразу після невдалого апдейту).

## Чому venv — окремий на кожну версію, а не спільний

Спільний venv, оновлюваний `pip install` на кожен реліз, уже раз ламав
свіжий інстал (`mcp>=1.0.0` без стелі → SDK 2.0 → `ModuleNotFoundError`,
див. `topics/install-lifecycle.md`, рішення #29). При спільному venv:
відкат коду **не** відкочує залежності назад (стара версія коду отримує
новіші пакети, ніж очікує), і навпаки, апдейт вперед може впасти на
`pip install` (мережа, знята з PyPI версія) уже після того, як код
перемкнутий.

Рішення: **окремий venv на версію**, будується під час підготовки (поки
стара версія ще активна), і при відкоті на попередню — її venv **вже
готовий**, нічого не перевстановлюється, відкат швидкий і без мережі.

## Механіка застосування — не саморедагування процесу

Процес не підміняє власні файли, поки виконується (на Windows файли
заблоковані на запис; жоден процес не може надійно вбити сам себе посеред
заміни й самостійно піднятись). Натомість:

1. API-хендлер качає tarball релізу в staging (`state/tmp/...`), розпаковує
   в `versions/<tag>/` — цілісність спирається на TLS, без окремої
   SHA-звірки (GitHub Releases API не дає checksum авто-архіву тегу);
2. створює venv у цій же теці, `pip install -r requirements.txt`;
3. **спавнить detached** процес (як наявний `service_ctl.spawn_detached`),
   який робить `stop → repoint junction → start → чекати /health`;
4. якщо health не відповів за таймаутом — детач відкочує junction назад і
   стартує стару версію.

Це максимально перевикористовує вже написаний і перевірений код
`install.ps1`/`.sh` (stop/mirror/deps/start/health-wait), а не пише другий
шлях оновлення поруч із першим.

## Нюанс, який версійний venv відкриває для лаунчера

`bin\mnemo.exe` сьогодні — ймовірно entry-point, згенерований pip'ом
**всередині одного конкретного venv** (шлях до python.exe зашитий на етапі
установки). Якщо venv стає версійним, верхній лаунчер має лишитись
**стабільним місцем** (алiас/PATH на нього не змінюється), а сам він — стати
тонкою обгорткою, яка **під час запуску** резолвить `current` (junction) →
`.venv/Scripts/python.exe` цієї версії, замість мати шлях до python зашитим
на етапі білда. Інакше перше ж перемикання версії ламає виклик команди
`mnemo` для всіх проєктів одразу.

**Підтверджено спайком 2026-08-20 (крок 0), з конкретним механізмом:**
`mnemo_bootstrap.py` переписаний на subprocess-диспетчер
(`current/.venv/Scripts/(python|pythonw).exe -m src.cli <argv>` зі
успадкованим stdio), і `service_ctl.py` **не потребує жодних правок** —
`windowless_python()`/`_default_target()` автоматично резолвять версійний
інтерпретатор/корінь, бо на момент їхнього виконання диспетчеризація вже
відбулась і код виконується всередині venv `current`-версії.

Один момент, який спайк знайшов емпірично (не був очевидний з дизайну):
**`sys.prefix`/`sys.executable`/`__file__` для пошуку `ENGINE_HOME`
непридатні** — усі три лишаються прив'язані до того venv, в якому
`pip install --no-deps` зібрав exe **на етапі білда**, незалежно від того,
звідки exe реально запущено (перевірено: скопійований exe в іншу теку й
далі показує старий шлях). Придатний **лише `sys.argv[0]`** — він
відображає реальне місце запуску. Тому `_engine_home()` тепер
`Path(sys.argv[0]).resolve().parent.parent` (`bin/mnemo` → `bin` →
`ENGINE_HOME`), а не через `sys.prefix`, як було раніше.

**POSIX не симетричний за механізмом, але простіший:** `install.sh`'s
`bin/mnemo` — не скомпільований артефакт, а bash-скрипт, який і сьогодні
резолвить `HOME_DIR` заново з `$BASH_SOURCE` при кожному виклику — жодної
"зашитої на білді" проблеми там немає в принципі. Зміна — один рядок
(`$HOME_DIR/.venv/bin/python` → `$HOME_DIR/current/.venv/bin/python`), але з
пасткою: інлайновий `sys.path.insert(0, os.environ["MNEMO_HOME"])` теж має
вказувати на `$HOME_DIR/current`, тоді як сама змінна `MNEMO_HOME` має
лишитись **не версійною** (`$HOME_DIR`), бо `state/`/`model-cache/` мають
лишатись спільними. Тобто два різні поняття "engine home" (версійний корінь
коду проти спільного кореня стану) — та сама розколка, яку довелось зробити
явною і у Windows-диспетчері.

**Відкрито, не блокує кроки 1–4:** Ctrl-C на foreground-виклику
(наприклад, `mnemo search` під час очікування) не перевірено емпірично —
немає інтерактивного TTY в середовищі спайку. Аргументовано з семантики
Windows process groups (дочірній процес не отримує `CREATE_NEW_
PROCESS_GROUP`/`CREATE_NEW_CONSOLE`, тож ділить консоль з батьком і отримує
Ctrl-C напряму), але це — ручна перевірка людиною за реальним терміналом,
яку варто зробити колись перед випуском, не зараз.
