# Встановлення, знесення, міграція з v2

Що інсталятор робить із машиною і чому оновлення на місці нічого не доводить.
Проводка проєкту — `topics/project-wiring.md`.

## Два рівні, які не збігаються в один

Інсталятор (`install.ps1` / `install.sh`) = **вся машина** однією командою,
аж до `doctor`. `mnemo init` = окрема команда **на теку проєкту**, і тільки
користувач знає, яка це тека.

Зупиняти сервіс руками перед оновленням **не треба** — інсталятор сам робить
`stop → refresh → start`.

## Знесення — дзеркало інсталятора

`uninstall.ps1` / `uninstall.sh`, за замовчуванням усе разом із моделлю;
`-KeepModel` / `-KeepState` / `-DryRun` / `-Yes`. `HOME` і linger не чіпає
**ніколи**.

Єдине, що **не відновлюється** з `.md`, — `banks.json`, тож банки друкуються
перед видаленням, а після перевстановлення потрібен новий `init` у **кожному**
проєкті.

## Оновлення на місці не перевіряє обіцянку «клонуй і постав»

Воно працює на **вже зарезолвленому** venv. Перевіряє лише встановлення
**з нуля** — так і знайшлася зламана залежність, невидима для всіх, хто вже
мав рушій. Тому **мажори пінуються**: `mcp>=2.0,<3` (рішення #29).

## `service start` чекає на `/health`

«Started» означає «відповідає». Готовність визначає `/health`, **не** живучість
породженого PID — на Windows це заглушка-редиректор, яка вмирає, поки бекенд
працює.

## Осиротілі індекси

Індекс зветься `sha1(корінь)[:16].db` — звʼязок **односторонній**, тож зняті
банки лишають осиротілі файли в `state/`. `doctor` їх рахує, `clean-orphans`
видаляє (питає перед тим); автоматично — **ніколи**.

## Міграція з v2

**Ознака v2 на машині** — немає `banks.json`, але є `.db`. Однозначно й
безпечно: без реєстру **жоден** індекс не належить живому банку. Інсталятор
чистить їх через `clean-orphans --yes`, знімок робить **до** дзеркалення.

**Список v2-проєктів зі `state/` не відновлюється в принципі**: імʼя файлу —
`sha1(корінь)`, а v2-база **не має таблиці `meta`**. Джерело — `~/.claude.json`
→ `projects` (абсолютні шляхи). `~/.claude/projects/` не годиться: назви тек
зводять `:`, `\` і `_` **усі** до `-`.

## `isatty()` під Git Bash на Windows бреше

Віддає True при `< /dev/null`. Для «чи є людина» потрібен
`GetFileType == FILE_TYPE_CHAR`, як `IsInputRedirected` в `install.ps1`.

## `get.ps1`/`get.sh` тепер тягнуть останній реліз, не `master` (2026-08-22)

Дефолтне джерело для one-liner-бутстрапу змінено: раніше — фіксований
`refs/heads/master` (бо релізу не існувало); тепер — резолв
`GET /repos/<repo>/releases/latest` (`tag_name`) і завантаження
`refs/tags/<tag>` з codeload, той самий підхід, що вже описаний для
`engine_update.py`'s `check_latest_release`. Порядок пріоритету:
`MNEMO_GET_ARCHIVE_URL` (повний оверрайд, як і раніше) → `MNEMO_GET_REF`
(явна гілка, `refs/heads/<ref>`, для ручного тестування нетегованої гілки)
→ резолв релізу (дефолт) → фолбек на `master`, якщо lookup впав (немає
релізів, GitHub недоступний, rate-limit) — фолбек, не жорсткий фейл, бо
one-liner не повинен ламатись через один невдалий API-виклик. Новий
тест-only оверрайд `MNEMO_GET_RELEASE_API_URL` — лише для підміни самого
lookup-URL у тестах, підміняти кінцевий codeload-URL і далі нема чим (навмисно
— `get.ps1` без параметрів на свій задум, зайвий важіль тут не потрібен
реальному користувачу).

Заразом виправлено застарілий тест `test_check_latest_release_real_no_releases_yet`
(`tests/test_engine_update.py`) — стверджував 404 на `DIMKA4621/mnemo`, що
було правдою, поки релізу не існувало; тепер v3.0.0 опубліковано, і той самий
запит справді повертає тег. Перейменовано на `test_check_latest_release_real_own_repo`,
асерти інвертовано на «тег реально приходить» — той самий клас бага, що вже
ловили в `logs/2026-08-22-posix-test-stale-assert-ci-red.md` (тест лишився
застряглим на «до фікса» стані вже після того, як стан змінився насправді).

## Прогрес-індикатори на довгих кроках install.ps1/install.sh (2026-08-22)

`pip install -r requirements.txt` і `mnemo warmup` (~2.2 ГБ) раніше йшли
мовчки — на повільному звʼязку виглядало як завислий скрипт. Обидва тепер
обгорнуті в heartbeat-хелпер: крапка що ~секунду, поки команда працює у
фоні, підсумок `done (Ns)`, повний вивід captured і показаний лише при
падінні (успішний прогін лишається таким же тихим, як і раніше — просто не
нерухомим).

`install.ps1`: `Invoke-CheckedWithHeartbeat` — навмисно **не** `Start-Process
-ArgumentList` (той джойнить масив у рядок без лапок навколо елементів з
пробілами — `-InstallHome` під `C:\Program Files\...` тихо розпалось би), а
`Start-Job` із тим самим `& $fp @fargs`, що й усюди в цьому файлі — лічильник
живий лише для того, щоб можна було раз на ~0.7с надрукувати крапку, а не
заради паралелізму.

`install.sh`: `run_with_heartbeat` — фонове `&`, `kill -0 $pid` у циклі під
`sleep 1`, `wait "$pid"` за кодом виходу; лог у `mktemp`, дампиться в stderr
лише на неуспіху. Виклик без `if`/`||` під `set -e` абортує скрипт так само,
як і прямий виклик раніше (перевірено живцем ізольованим тест-скриптом, не
лише читанням коду).

## Небезпечний інцидент: `get.ps1` без `-InstallHome` зачепив реальний `~/.mnemo`

Ad hoc перевірка fallback-гілки (release lookup впав → мав повернутись на
`master`) була запущена **без** `-InstallHome`-ізоляції, з розрахунком, що
короткий таймаут захистить. Не захистив: `install.ps1` встиг реально
зупинити справжній сервіс, перебудувати `versions/local/` зі свіжозавантаженого
GitHub `master` і перемкнути `current` на нього — на **реальній машині
користувача**, поки self-update-стан (`state/engine_version.json`) лишався
на `v3.0.0`. Дані (`state/`, `model-cache/`, реєстр банків) не постраждали —
це гарантія install.ps1, і вона підтвердилась, — але `current` розійшовся з
тим, що self-update вважав активним. Виправлено вручну через той самий
`service_ctl.switch_current("v3.0.0")`, яким користується реальний update-apply
(stop → switch_current → start), не переінсталяцією.

**Урок, без винятків надалі: жоден живий запуск `get.ps1`/`install.ps1` не
відбувається без явної ізоляції (`-InstallHome`/`--home` на тимчасову теку),
навіть для швидкої ручної перевірки одного рядка виводу.** Короткий
`timeout=` у Python-обгортці — це захист від зависання тесту, а не від
побічного ефекту: якщо процес встигає хоч щось зробити до вбивства, воно вже
зроблено.
