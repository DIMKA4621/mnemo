# 2026-08-21 (п'яте) — `/api` типово відкритий, без токена

Design decision #34 (`Memory-design-v3.md` §13).
Продовження того самого дня, окремо від порт-ренумерації/idle-timeout/home-move (`2026-08-21-port- renumber.md`).

## Запит і межі

Користувач попросив прибрати логін-токен кабінету: "цей кабінет зараз базово локальний" — токен-гейт на кожен свіжий `mnemo ui` купував тертя, не реальний захист.
Явно звузив межі, коли я запропонував ширший вибір (окремо `/mcp-admin`/`/mcp-tools`): "тільки про токен при вході в ЮАЙ і все" — `/mcp`, `/mcp-admin`, `/mcp-tools` не чіпати взагалі.
Генерація токена пізніше (`mnemo ui token generate` чи щось таке) — явно відкладена, не будується зараз.

## Що змінено

**`src/api.py`:**
- `_configured_token()` — новий peek-хелпер: чи налаштовано токен (env `$MNEMO_API_TOKEN`, або персистентний `state/api.token`), **не мінтячи** його.
  Відрізняється від `api_token()`, який завжди мінтить-якщо-нема — той лишається для `/mcp-admin`/`/mcp-tools`, яким токен потрібен завжди.
- `auth_middleware`: `/api/*` тепер окрема гілка — пропускає запит, якщо `_configured_token()` повертає `None`; якщо токен налаштовано, поведінка та сама, що й раніше (точне співпадіння, 401 інакше).
- `lifespan()` більше **не** кличе `api_token()` жадібно при старті — якби кликав, файл існував би одразу після кожного запуску сервісу, і "типово відкритий" ніколи не було б правдою на практиці.
  Токен і далі мінтиться, але **ліниво**, першим реальним зверненням до `/mcp-admin` або `/mcp-tools`.
- `/api/doctor`: раніше жорстко звітував `"present": true` (бо токен завжди існував).
  Тепер читає `_configured_token()` і чесно каже `present: false`, коли нічого не налаштовано.

**`src/cli.py`:** `_cmd_ui()` друкує голе посилання `.../ui/`, без `?token=`, коли `client.token` порожній; якщо токен таки налаштовано — дописує `?token=` як і раніше (наперед сумісно з майбутньою командою генерації).

**`src/webui/static/app.js`:** `boot()` більше не підіймає token-gate, якщо `token` порожній — одразу `start()`.
Уся інша gate-машинерія (`resolveToken`, `openGate('rejected')` на справжній 401, bank-token панель — зовсім інша річ, токен банку для `/mcp`) лишена недоторканою: працює й далі на випадок, якщо колись налаштують сервісний токен.

**`src/diagnostics.py`, `page-settings.js`:** текст рядка "api token" переписано — "не встановлено" тепер нейтральний дефолтний стан, а не "MISSING"-тривога.

**Тести**, зламані видаленням жадібного мінтингу (обидва спирались на `api.token`, що завжди існує одразу після старту, і слали `Authorization: Bearer` на `/api` запити):
- `tests/test_service_recovery.py` — прибрано `token()`-хелпер і заголовки Authorization на двох `/api` POST-запитах.
- `tests/test_update_auto.py` — прибрано `token()`-хелпер і заголовки Authorization на `_get`/`_post`/`_put`; коментар про `os.environ.pop ("MNEMO_API_TOKEN", ...)` переписаний — причина попу тепер не "інакше token() нічого не знайде", а "інакше успадкований реальний токен примусить /api вимагати автентифікацію в тесті, що її не шле".
- `tests/test_mcp.py` — логіка не зламана (цей тест іде проти **живого** сервісу, а в ньому `api.token` вже існує з попередніх сесій; сам тест і так SKIP-ає з exit 2, якщо файла нема, рядок ~174), лише коментар біля перевірки `/api` уточнює нову умовність.

## Перевірка

Живцем, ізольованим throwaway-інстансом (venv `~/.mnemo/versions/local/ .venv`, окремий `MNEMO_STATE_DIR`/порт, не чіпаючи реальний сервіс користувача):
1. Без будь-якого токена: `GET /api/status` без заголовка → 200; з довільним неправильним → теж 200 (відкрито).
   `POST /mcp-admin` без токена → 401 (незмінно).
   `api.token` НЕ створюється сам по собі — тільки реальне звернення до admin/tools із **непорожнім** presented токеном доходить до `api_token()` (сам `_token_ok` рано виходить на `if not presented`, це старий код, не мій).
2. З `$MNEMO_API_TOKEN` виставленим: `GET /api/status` без токена → 401; з неправильним → 401; з правильним → 200. `/api/doctor` показує `present: true`.
3. `mnemo ui` у безтокенному режимі друкує голе `http://127.0.0.1:<port>/ui/`.
4. `mnemo doctor` рядок: `api token        not set — /api is open on loopback by default (...)`.

**Не запускався:** повний `tests/test_service_recovery.py` через `__main__` (той файл ще й реєструє справжню задачу Task Scheduler у другому тесті — недоречний побічний ефект лише заради перевірки auth-зміни).
Не перевстановлено `~/.mnemo` (`install.ps1` не запускався) — зміна лишається в репозиторії, не в живому рушії, доки користувач не попросить перевстановити.

## Що НЕ зачеплено (свідомо)

`/mcp` (токен банку — адреса, не просто auth), `/mcp-admin`, `/mcp-tools` — усі й далі завжди за сервісним токеном, як до цього.
Bank-token панель у кабінеті (генерація/показ токена банку для `.mcp.env`) — окрема річ, не займана.

## Живе розгортання (`install.ps1`, реальний `~/.mnemo`) — два реальні
## пропуски знайдені й закриті

Після першого коду-проходу користувач попросив реально розгорнути (`install.ps1`, перезапуск живого сервісу).
Це виявило **дві речі, пропущені в первинній реалізації** — обидві знайдені й закриті в тому ж проході:

1. **`/ws` (WebSocket, живий прогрес кабінету) мав свою окрему перевірку `_token_ok(token)`, не пов'язану з `/api`'s `auth_middleware`.** `_token_ok(None)` рано виходить (`if not presented: return False`) — тобто без жодного токена `/ws` просто **відмовляв** у підключенні (код 1008), навіть у "відкритому" режимі: сторінка кабінету завантажилась би, а живий канал — ні.
   Виправлено симетрично до `/api`: перевірка токена на `/ws` тепер теж умовна на `_configured_token()`.
2. **Сам `install.ps1`/`install.sh` мінтили й експортували `MNEMO_API_TOKEN` як постійну змінну середовища (`Set-ApiTokenEnvironment` на Windows, аналогічний блок в install.sh), якщо її ще не було.** Це і є те саме "автоматичне встановлення/підстановка токена", про яке користувач просив із самого початку задачі — але це в installer-скриптах, не в `api.py`, тож перший прохід це пропустив.
   Обидва інсталятори мали свою версію коментаря "the git-tracked .mcp.json refers to `${MNEMO_API_TOKEN}`" — **застаріла причина**: реальний `.mcp.json.template` адресує **токен банку** через `{{MNEMO_TOKEN}}`, не `MNEMO_API_TOKEN` узагалі; ця функція, схоже, лишилась із покоління архітектури до появи токенів на банк.
   Прибрано обидва блоки, плюс виправлено текст `-Check`/`--check` звітів (Windows і POSIX) — "missing (created on first service start)" уже неправда (мінт тепер лінивий, не при старті сервісу), переписано на "not set — /api is open by default".

**Пастка під час діагностики, варта пам'ятання:** на цій машині `MNEMO_API_TOKEN` вже була постійною User-змінною Windows (з часів, коли токен був обов'язковим) — видалення реєстрового значення (`[Environment]::SetEnvironmentVariable(..., $null, "User")`) **не впливає на вже запущені процеси**, включно з тим самим Bash/PowerShell, з якого викликається видалення: кожен наступний spawn з того самого процесу й далі успадковує старе значення, доки не буде явно знято (`Remove-Item Env:\MNEMO_API_TOKEN` / `env -u MNEMO_API_TOKEN` саме для того конкретного виклику) або не відкриється справді новий термінал.
Це і ввело в оману на кілька ітерацій: здавалося, що `state/api.token` "сам відроджується" після видалення — насправді `install.ps1`, викликаний із зараженої оболонки, щоразу re-export'ив ту саму стару змінну заново в реєстр, і кожен наступний `mnemo doctor`/`ui`, викликаний з тієї ж зараженої оболонки, теж бачив її.
Розплутано лише після прямої живої перевірки: `python -m src.cli serve` напряму (в обхід `service_ctl`/`windowless_python`) в свіжому процесі підтвердив, що сам бекенд-код і не думав мінтити токен сам по собі.

**Фінально підтверджено на реальному `~/.mnemo` (не throwaway):** `mnemo doctor` → `api token        not set — /api is open on loopback by default`; `mnemo ui` (у справді чистому оточенні, `env -u MNEMO_API_TOKEN`) → голе `http://127.0.0.1:4646/ui/`, без `?token=`.
`state/api.token` лишається відсутнім і стабільним після перезапуску сервісу й після паузи.
4 банки, резидент, бекенд — усі здорові.
