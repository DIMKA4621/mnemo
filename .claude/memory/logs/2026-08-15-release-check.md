## RX 580 таки тягне Ollama — це не було очевидно

`ollama ps` → **`100% GPU`**. ROCm цю карту офіційно не тримає, тож очікувався
тихий відкат на CPU; його немає. Тепла пропускна на батчі 16 чанків —
**~3340 симв/с**, розкид трьох проходів 2%.

Перший запит після простою — **8.4 с** (завантаження моделі у VRAM, 664 МБ).

## Резидент коштує 1.5 ГБ і не вивантажується сам

`MNEMO_EMBED_IDLE_TIMEOUT` за замовчуванням **`0` = ніколи**; у коді прямим
текстом «the resident no longer idle-exits». Тобто раз піднявшись, тримає
пам'ять до перезавантаження машини.

**RSS гуляє в межах одного процесу: 416 МБ → 1502 МБ.** Той самий pid, та
сама модель; схоже на ліниве завантаження ONNX — до першого ембедингу
мінімум, після нього повний розгін. Міряти резидент до першого запиту —
означає недоміряти втричі.

Час повернення після вбивства (`local`, CPU): **7624 мс холодний пошук**
проти **742 мс теплого**. Тобто підняття моделі ≈ 6.9 с.

Симетрія з Ollama (8.4 с) — обидва бекенди коштують ~7–8 с на пробудження,
тож і політика простою в них має бути однакова.

## Рішення: `OLLAMA_KEEP_ALIVE=3h`

Виставлено в user-змінну. Аргумент користувача, і він сильніший за `-1`:
ціна простою названа й мала (8 с раз на три години), а `-1` тримав би 664 МБ
**VRAM** цілодобово — на 4-гігабайтній карті це конкуренція з іграми й
рендерингом браузера.

**Пастка при застосуванні, варта запису.** Ollama читає змінну **на старті**,
тож потрібен перезапуск. Але перший перезапуск нічого не дав: `Start-Process`
успадковує середовище **поточної** сесії, а вона стартувала до того, як
змінну створили. Лікування — виставити `$env:OLLAMA_KEEP_ALIVE` у самій
сесії перед запуском дитини. Доказ — `UNTIL` у `ollama ps`: було
`4 minutes`, стало `3 hours from now`.

## Головна знахідка: `init` мовчить, коли пам'ять під `.gitignore`

Адоптовано реальний проєкт `E:\work_projects\python\indeedApplyBot` (18
файлів коду, git чистий, `.claude/` не було). `init` відпрацював правильно —
шаблон, `.mcp.env`, обидва `mcp-setup`, банк зареєстровано, індекс за 857 мс.

Але в проєкту в `.gitignore` є `**/.claude`, і тому:

```
$ git check-ignore -v .claude/memory/MEMORY.md
.gitignore:7:**/.claude    .claude/memory/MEMORY.md
```

**Пам'ять, щойно створена `init`, ігнорується git — і `init` про це не
сказав.**

Чому це вада, а не дрібниця:

1. Обіцянка «пам'ять їде з комітом» повторена всюди, зокрема в правилі, яке
   `init` **сам щойно поклав** у цей проєкт: «Only the project's
   **git-tracked** `.claude/memory/` counts». Тобто система пише інструкцію,
   якої в цьому проєкті не може виконати.
2. `init` **уже вміє дивитись у git саме тут** — він щойно дописав
   `.mcp.json` і `.mcp.env` у `.gitignore`, бо ті тримають токен. Механізм є,
   просто дивиться в один бік.
3. `**/.claude` — **поширена звичка**, а не екзотика: люди виносять із git
   локальні налаштування Claude Code. Перший же реальний проєкт, узятий
   навмання, його мав.

Симптом у житті: людина пише пам'ять, комітить, на іншій машині банк
порожній. Дізнається найпізніше з можливого.

**Правильна поведінка** — не мовчати: перевірити `git check-ignore` на корені
банку і, якщо ігнорується, сказати вголос і запропонувати виняток:

```gitignore
**/.claude
!.claude/memory/
!.claude/rules/
```

Мовчки правити чужий `.gitignore` не варто — це рішення проєкту. Але
промовчати означає дати обіцянку, яку система не виконує. **Не виправлено**,
записано як знахідку.

### Хибна тривога поруч, щоб не переслідувати вдруге

У `.gitignore` після `init` у консолі видно `mnemo ?" generated wiring`.
Це **не** зіпсований запис: байти у файлі — `\xe2\x80\x94`, коректний UTF-8
em-dash. Крякозябри дає консоль PowerShell (cp1252), файл цілий.

## Дрібне, але корисне

Свіжоадоптований проєкт дає банк **1 файл / 1 чанк** — у `.claude/memory/`
лежить лише якір `MEMORY.md`. Тобто «індексація нового проєкту» на чистому
adopt не міряє нічого: щоб перевірити поведінку під навантаженням (і пошук
**під час** індексації), банк треба спершу наповнити.

## `ollama list` показує модель, якої на диску немає

Перевірка перед переходом на Ollama (за підозрою користувача — він видаляв
модель руками у файлах). Підозра підтвердилась:

```
blobs на диску: 4 файли, 1104 МБ          <- вистачає рівно на bge-m3

```

Два маніфести, блобів на одну модель. Тобто **видалення файлів руками лишає
маніфест сиротою**, і `ollama list` до останнього рапортує розмір із
маніфесту, а не з диска. Впаде лише при спробі завантажити.

Для нашої роботи не заважає (йдемо на `bge-m3`), але це пастка для будь-кого,
хто вирішить перевіряти наявність моделі через `ollama list`.

**`bge-m3` перевірена по суті, а не за фактом відповіді:** `dim=1024`,
**`L2norm=1.0`** (нормалізовані вектори), значення осмислені. Це важливо:
модель, що завантажилась криво, все одно відповідає — нулями. Норма це ловить,
код відповіді 200 — ні.

## Зміна провайдера з кабінету: працює, але повідомлення веде не туди

Користувач сам перемкнув `local` → Ollama/bge-m3 через шестерню (навмисно
руками, щоб побачити шлях людини). Записалось усе правильно, служба підхопила
**без рестарту**:

```
provider api (bge-m3, dim 1024)  embed configured
voice-agent  api  local:multilingual-e5-large:1024  ready  846  <- REBUILD PENDING
mnemo        api  local:multilingual-e5-large:1024  ready  334  <- REBUILD PENDING
```

Але висновок користувача був «нічого не сталося». Дві причини, обидві наші.

### 1. `restart_required` захардкоджений `True` — і це неправда

```python
forget_providers()                              # кеш провайдерів скинуто ТУТ
return {..., "restart_required": True, ...}     # і все одно «перезапустіть»
```

Рядком вище код **сам** робить те, що знімає потребу в рестарті, і коментар
поруч це прямо пояснює. Напис описує стан, який був **до** появи
`forget_providers()`, і його забули прибрати.

Доказ на екрані: `pid=9764`, `up 13410s` — служба не перезапускалась, а
провайдер уже новий.

Ціна не в зайвому реченні, а в напрямку: людина йде шукати кнопку рестарту
замість того, щоб побачити, що система чекає команди на **перебудову**.

### 2. `REBUILD PENDING` є в терміналі й **немає** в кабінеті

`status` пише його прямим текстом; картка банку — ні. Це не відсутня фіча, а
**стан, який система знає й не показує**. Той самий рід вади, що `init`, який
змовчав про `.gitignore`: інформація є, людина її не бачить.

## Рішення: кабінет мусить уміти все, що вміє CLI

Пряма вимога користувача, і вона про принцип, а не про зручність: «все те
саме, що можу зробити командами, маю могти через UI» — інакше виходить
«натисніть тут, а доробіть у терміналі».

Зріз на сьогодні:

| дія | CLI | кабінет |
|---|---|---|
| пошук, дерево, журнал, статус | ✅ | ✅ |
| додати / прибрати банк, реіндекс, повна перебудова | ✅ | ✅ |
| MCP-доступ (токен), налаштування провайдера | — | ✅ |
| **`REBUILD PENDING` видно** | ✅ | ❌ |
| **перебудувати після зміни провайдера** | ✅ | ❌ |
| `doctor` | ✅ | ❌ |
| `clean-orphans` | ✅ | ❌ |
| `service`, `autostart` | ✅ | ❌ |
| `warmup` | ✅ | ❌ |

База симетрична; дірка проходить **по межі «машина проти банку»**.

### Куди що йде (розклад користувача)

- **Головний екран** — тільки `REBUILD PENDING`: банер зверху над списком
  банків, «усі банки очікують на перегенерацію, бо змінилась модель» +
  кнопка **Перегенерувати**. Це єдине з цього списку, що заслуговує головний
  екран, бо це стан **зараз** і він блокує сенс роботи.
- **Розділи налаштувань** (не головний екран): `warmup`, керування службою
  й автозапуском, `doctor`, `clean-orphans`. Потрібні рідко, тож
  «було б добре», а не пріоритет.

**Не реалізовано** — записано як черга робіт після наскрізної перевірки.

### Прискорення ~3×, а не 8.8× — і це не суперечність

Порівняння на повному конвеєрі: **283 чанки / 5.5 хв на CPU** проти
**334 / 1.9 хв на GPU**.

`embedding-throughput.md` записує 8.8×, і воно не спростоване: там міряли
**сам ембединг** на вирівняних токенах. Тут — уся індексація: читання файлів,
чанкування, HTTP до Ollama, запис у SQLite. GPU прискорює одну ланку з
чотирьох, тож наскрізне число мусить бути меншим.

**Урок на майбутнє: 8.8× не можна обіцяти як час перебудови.** Реальне
очікування для UI — **~3×**, і саме воно потрібне діалогу «перебудувати
зараз?». Мій власний розрахунок (~35 с для `mnemo`) промахнувся втричі саме
тому, що спирався на пакетне число.

### Якість після зміни моделі — не просіла

Ті самі чотири питання, що й до перемикання. **4/4, потрібний файл першим** —
збіг із базовою лінією повний, включно з крос-мовністю:

| питання | перший хіт (e5/CPU → bge-m3/GPU) |
|---|---|
| `why was the calibration button abandoned` | той самий |
| `orphaned indexes cleanup` | той самий |
| `чому 404 не має конверта помилки` | той самий |
| `Ollama GPU throughput measurement` | той самий |

Тобто прогноз із `embedding-throughput.md` («bge-m3 не гірша й не краща
настільки, щоб це побачити») справдився на живих даних.

**Пошук став повільніший: 0.86–1.6 с → 1.5–1.8 с.** Логічно — один запит це
один HTTP-виклик до Ollama проти локального резидента в пам'яті, а GPU на
одному короткому тексті майже не допомагає (в записах — 1.8× проти 8.8× на
пакеті). Тобто Ollama виграє **індексацію** і трохи програє **пошук**.

## ВАДА: перебудова через чергу створювала vec-таблицю НЕ тієї ширини

Найсерйозніша знахідка дня. Знайдена блоком 6 — переходом на OpenAI
(`text-embedding-3-small`, **dim 1536**), тобто першою зміною, де рухалась
**розмірність**, а не лише назва моделі.

Симптом: кожен файл падав однаково, банк лишався **порожній**.

```
OperationalError: Dimension mismatch for inserted vector for the
"embedding" column. Expected 1024 dimensions but received 1536.
```

### Причина — один пропущений аргумент

`workqueue._open_for_rebuild` кликав `store.reset_index(conn)` **без `dim`**.
Той параметр був необовʼязковий і падав назад на ширину зі **старої** meta —
тобто дропав `float[1024]` і створював `float[1024]` знову, для провайдера,
що вже слав 1536.

Той самий код у `index._open_bank` передавав `dim=provider.dim` **правильно**.
Два шляхи перебудови, розійшлися рівно на цьому.

### Чому не спіймалось раніше — і чому це страшніше, ніж виглядало

1. **e5-large і bge-m3 обидві 1024.** Перший перехід (`local` → Ollama) міняв
   модель, але **не** ширину, тож вада не проявилась. Наша ж памʼять
   попереджала: «найнебезпечніший випадок — коли розмірність збігається».
   Тут той самий збіг спрацював навпаки — **сховав** ваду.
2. `test_provider_change_rebuilds` міняв **лише модель** і йшов через
   `index._open_bank` — обидві сліпі плями одразу.
3. При розборі виявилось гірше: **перша ж bulk-збірка через чергу вже була
   зламана**. `connect()` створює таблицю дефолтними 1024, і витирання
   зберігало цю ширину — тобто провайдер будь-якої іншої ширини не працював
   **ніколи**, а не лише «після зміни».

### Найгірша частина: банк виглядає повним

`chunks_indexed=0`, а `chunk_count=5`. Текст у `chunks` пишеться, вектори —
ні. Тобто банк **не виглядає порожнім** — він виглядає наповненим і не
знаходить нічого. Тому тест перевіряє `chunks_indexed`, а не `chunk_count`.

### Виправлення (рішення користувача: «база зноситься завжди й повністю»)

- `store.reset_index(conn, *, dim: int)` — **`dim` став обовʼязковим**.
  Не косметика: саме «зручний» дефолт і дав ваду, а тепер забути його
  неможливо — код не запуститься. Фолбеку немає навмисно: викликач, який не
  знає ширини, не знає й для якого провайдера перебудовує.
- `workqueue._open_for_rebuild` передає `dim=provider.dim`.

**Ретрай свідомо НЕ додано** (обговорено): черга правильно спинилась після
провалу, а помилка була детермінована — повтор крутив би те саме по колу й
палив ключ на кожній ітерації. Ретрай доречний для мережевого збою; це інша
задача.

### Тест перевірено на регресії

`tests/test_pipeline.py::test_rebuild_survives_a_dimension_change` — через
**чергу** (не `index`) і зі **зміною ширини** (64 → 192 на `HashProvider`,
який тепер приймає `dim` у конструкторі). Обидві половини потрібні: сама
ширина через `index` пройшла б, сама черга при незмінній ширині — теж.

На зламаному коді: **3 FAIL** + виняток на пошуку (`Expected 64, received
192` — той самий текст, що на живій системі). Після виправлення — **75/75**,
`test_platform` 263/263.

### Наскрізне порівняння трьох бекендів на банку `mnemo`

| бекенд | чанків | індексація | пошук |
|---|---|---|---|
| `local` e5 (CPU) | 283* | ~5.5 хв | 0.86–1.6 с |
| Ollama bge-m3 (GPU) | 338 | 112 с | 1.5–1.8 с |
| **OpenAI 3-small** | **341** | **20 с** | **1.33–1.46 с** |

**не повільніший** за Ollama, хоча йде через інтернет — на одному короткому
тексті мережева затримка порівнянна з чергою до локальної GPU.

Ціна: ~0.3 цента за 341 чанк (`3-small`, $0.02/M токенів). Тобто повна
перебудова обох банків — менш ніж пів цента.
