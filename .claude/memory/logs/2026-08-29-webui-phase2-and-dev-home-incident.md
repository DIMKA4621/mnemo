## Incident: verifying against the real `src.api:app` shares the user's live `~/.mnemo` home — don't do this again without isolating it

While independently verifying the `by_bank` fix, the lead spun up the real `src.api:app` (not the fixture mock) directly from the working checkout via `uvicorn.run(...)`, using the installed engine's venv python but **without overriding `MNEMO_HOME`/state dir isolation for the engine home itself** (only `MNEMO_STATE_DIR` was set to a scratch path — the shared `~/.mnemo` root, including `versions/`, was still the real one). The app's background self-update checker fired (visible in its own log: a live `GET https://api.github.com/repos/.../releases/latest`) while this scratch instance ran concurrently with the user's actual live service (also `v3.2.0`, same shared engine home).

Result: within that window, `~/.mnemo/versions/v3.2.0/.venv/Scripts/` was rewritten and `pyvenv.cfg` went missing from that venv (confirmed via both git-bash and native PowerShell `Test-Path`) — the venv can no longer start a fresh Python process (`No pyvenv.cfg file`), though the **already-running** live service (PID confirmed distinct from the scratch instance) kept working fine in-memory and was still healthy afterward (`/api/status` returned 200, banks intact). Root cause not fully diagnosed (out of scope to chase further per the user) — leading hypothesis is the self-update checker in the scratch instance staging/touching the shared `current`/`v3.2.0` version directory while it collided with the real service's own lifecycle. Not confirmed with certainty.

**Mitigation taken**: backed up all 5 bank `.db` files + `banks.json` + `api.token` + `settings.json` + `mnemo.env` to `C:\Users\dima\mnemo-state-backup-2026-08-29\` (outside `~/.mnemo`, so a from-scratch reinstall + `mnemo init` per project wouldn't need a full reindex — the raw index files are the expensive-to-regenerate part). User's call: not urgent to fix the broken venv right now ("похуй на ту версію" — will do one clean reinstall later whenever convenient); the live service currently running doesn't need to be touched or restarted for this to be a non-issue in practice.

**Binding rule going forward**: never point a manually-spun-up real backend instance (`uvicorn.run` against `src.api:app`, or any other direct verification run of the real service code) at the user's actual `~/.mnemo` — not even via `MNEMO_STATE_DIR` alone. Give it a fully separate, isolated home directory (an env var overriding the *whole* engine home, not just the state subdir — check `src/config.py` for the actual override the codebase supports before doing this again) so its self-update checker, version directory, and everything else stay quarantined from the user's live install. The user previously kept a dedicated `mnemo-dev` home for exactly this reason in earlier sessions — revive that pattern rather than reusing the real one, even for a "quick" verification.
