**Critical security bug caught by reviewer, real exploit proven via HTTP**: `_validate_link_name_path_safe` missed Windows drive-letter-anchored names (`"C:foo"`) — `pathlib`'s `/` operator treats a drive-anchored segment as a NEW anchor, silently discarding the joined root (`Path("/safe/root") / "C:foo"` == `Path("C:foo")`, not `Path("/safe/root/C:foo")`). Reviewer sent a real HTTP request and got a 201 with a file written to `C:\` outside the agent sandbox. **Fix pattern** (now the template for any future path-from-user-input code in this codebase): `candidate.resolve().is_relative_to(root.resolve())` containment check — this closes the *entire* anchor-trick class (not just drive letters — also catches UNC paths, `~` expansion tricks, etc.), rather than trying to enumerate and reject specific dangerous patterns. Added alongside: a denylist of NTFS-invalid chars/reserved device names, and an `OSError`→`InvalidLinkName` safety net for whatever the denylist misses.

**This exact bug class recurred in MN-43's review** (see below) as a thing reviewers now check for by default — worth remembering: *any* new feature that builds a filesystem path from user/agent-controlled input needs this containment check, not case-by-case validation.

## MN-43 — agent_runtime.py: resident PTY-based live chat runtime

The last piece before the frontend chat console (MN-44) can be built. Full plan from `planner`, two flagged open questions resolved by the lead directly rather than asking the user:

1. **custom-mode → real `claude` invocation** (undocumented anywhere until now): `host`/`port` → `ANTHROPIC_BASE_URL=http://{host}:{port}` env var (the one well-documented mechanism Claude Code CLI has for pointing at a proxy); `model` → `--model <value>` CLI flag; `extra_args` → appended verbatim to argv. `autocompact` has no known CLI/env mechanism — deliberately NOT translated, left as a code comment rather than guessing at a flag that might not exist. This resolved what the planner called a genuinely blocking documentation gap — decided rather than deferred, so MN-43 needed no further 43.5 sub-phase.
2. **Soft concurrency ceiling**: 8 concurrent live sessions machine-wide (`config.MAX_LIVE_SESSIONS`), 409 `too_many_sessions` past that. Adopted as cheap abuse/bug insurance (double-click, UI bug forking real paid processes) — explicitly NOT the same as MN-46's future tuned real policy.

**Architecture**: `src/agent_runtime.py` (new), `_sessions: dict[chat_id, Session]` purely in-memory (no process "adoption" across a service restart — deliberately sidesteps the whole PID-reuse danger class the codebase has been burned by before, per `v3-build.md`'s standing rule about never identifying a process by anything but a live in-memory handle or a checkable external fact). Lazy spawn on first WS subscriber (never on chat *record* creation — creating the metadata is free, spawning `claude` costs real API usage). `chats.json` + per-chat `history.log` extend `agent_registry.py` (not a separate module). WS route `/ws/agents/{slug}/chats/{chat_id}` behind the same service-token gate as the existing `/ws`. Race-free reconnect: one lock per `Session` covers history-append + subscriber-fanout + new-subscriber-registration as one atomic unit — this is what actually prevents lost/duplicated output across a reconnect, not just a test asserting it works.

**Real-spawn discipline held**: only 1 real `claude` CLI invocation used for the entire ticket's live verification (isolated `MNEMO_HOME`, script kept at `.claude/scratch/mn43-verify/real_spawn_check.py`), well under the 2-3 budget the ticket set. Confirmed the full live chain in one go: spawn → real model response → second subscriber doesn't trigger a second spawn → broadcast to both → clean stop → history.log persists after termination.

**Reviewer found 2 real bugs, both fixed, re-verified before commit** (`4f4baa2`):
1. `_spawn_session`: if anything after the real PTY process was created (most plausibly `history_path.open()`) raised, the exception propagated with the live process never added to `_sessions` — an orphaned, unstoppable, still-billing `claude` process. Fixed: wrap post-spawn steps in try/except, `proc.terminate(force=True)` under `suppress(Exception)` before re-raising.
2. `stop_all()`'s docstring/`api.py`'s shutdown comment both claimed parity with `workqueue.stop()`'s two-phase "signal all, then join all" shutdown shape, but the actual code called `stop_session()` per chat_id serially — each one doing terminate-then-join-with-full-timeout before moving to the next. With N live sessions this bounds shutdown time at N × timeout instead of one shared timeout — "a fixed timeout a real workload exceeds," a pattern this project has hit before (see `service_ctl`/`workqueue` history). Fixed to genuinely mirror `workqueue.stop()`: phase 1 terminates every session (no join), phase 2 joins every reader thread.

**POSIX caveat, explicit and unresolved**: `ptyprocess`-based POSIX branch is written to a symmetric API but has never run — dev machine is Windows-only. Needs a real Linux/macOS verification pass at some point; not blocking, just genuinely unverified rather than silently assumed to work.

## Recurring pattern worth remembering

The MN-48 path-containment fix (`candidate.resolve().is_relative_to(root.resolve())`) is now the house style for validating any filesystem path built from user/agent-controlled input in this codebase — reviewers check for its absence by default on any new feature touching agent-scoped paths. MN-43's chat_id paths didn't need it (chat_id is always server-generated via `uuid.uuid4().hex`, never taken from client input before path-building), but the reviewer explicitly checked for the *pattern's applicability* rather than assuming it was fine, which is the right instinct going forward too.

## MN-44 — frontend live chat console (xterm.js), 2 phases, both committed

- **Phase A (`20fac8c`, backend)**: `POST /api/agents/{slug}/chats/{chat_id}/upload` (streamed, size-limited via `config.MAX_CHAT_UPLOAD_BYTES`=25MB default, sanitized filename + MN-48's `is_relative_to()` containment check as belt-and-suspenders on top of the sanitizer) and `GET /api/agents/{slug}/subagents` (best-effort `.claude/agents/*.md` frontmatter scrape, hand-written parser rather than adding a PyYAML dependency for a display-only feature). Reviewer caught one real bug: the file-read loop caught only `OSError`, but `UnicodeDecodeError` (raised by a non-UTF-8 `.md` file) is a `ValueError` subclass — one bad file 500'd the entire subagents listing instead of being skipped. Fixed with `except (OSError, UnicodeDecodeError):`.
- **Phase B (`746a529`, frontend)**: `ChatConsole.tsx` — confirmed **not** a chat-bubble UI, a faithful minimal xterm.js terminal (the ttyd/gotty/wetty pattern): `term.onData` forwards every keystroke raw, no custom input box, no slash-menu, no model picker — the real CLI's own TUI (thinking display, tool calls, autocomplete, line editing) renders itself via ANSI, which is the entire reason MN-43 chose PTY over Agent SDK structured events in the first place. `term.reset()` before every write on connect/reconnect (replay and live share one write path) matches `agent_runtime.py`'s full-history-replay-then-live contract exactly — no client-side dedup logic needed anywhere. Switching chats only closes the WebSocket, never calls stop/delete — background generation is never interrupted by navigation, confirmed by grep + live network-log inspection. File drag-and-drop uploads through Phase A's endpoint and injects the resulting path as literal terminal input text (the conservative fallback, independent of whatever real paste mechanism the CLI itself might support — never confirmed, corroborating opinion only, not blocking since the fallback works regardless of the answer).
- **A key decision along the way**: the existing static mockup (`.claude/scratch/agents-console-mockup/`) turned out to be built for the wrong data model entirely — structured Claude Agent SDK events (chat bubbles, thinking panels, tool-call cards), not MN-43's byte-level PTY stream. It was **not portable as a component** — only its CSS tokens and outer chrome shape survived into the real implementation. Worth remembering: a mockup built before the real backend contract exists can encode assumptions the real backend later invalidates: always re-verify a mockup's data model against the actual shipped API before porting it, don't assume "it was designed for this feature" means "it matches this feature's real wire format."
- **Scope decision, recorded for future readers of `docs/Agents-v1-scope.md` §3**: that doc's "send AND display" file/image requirement is satisfied only for the human's own OUTGOING attachment (a chip/thumbnail in the browser DOM). Images appearing IN the agent's own output are explicitly NOT rendered specially in v1 — the CLI doesn't emit an inline-image terminal protocol (iTerm2/Kitty/Sixel or otherwise) mnemo could hook into, and even if it did, that would be outside mnemo's control to render via xterm.js's text-only model. `docs-keeper` still needs to fold this narrowing into `Agents-v1-scope.md` §3 itself — not yet done as of this log entry.

## MN-49 — new ticket, split off from MN-44 Phase B's live verification

Real, twice-reproduced bug found live-testing reconnect after a mid-session browser resize: pre-resize portions of `history.log` replay corrupted (overlapping/misplaced text). Root cause: `agent_runtime.py`'s `history.log` is a raw append-only PTY byte stream carrying **absolute ANSI cursor-position codes relative to whatever terminal width was active when they were written** — replaying the whole buffer into a terminal now sized differently breaks any such codes from before the resize. Confirmed by an independent reviewer to be **inherent to the storage format**, not something `ChatConsole.tsx` could reasonably work around client-side (the frontend already does the only sane thing — `fit()`+resize-to-current-width happens synchronously on connect, before any replay `output` chunk is written, which is precisely what makes the mismatch visible rather than something a different client-side ordering could avoid). Filed as MN-49, linked "Relates" to MN-43, explicitly does not block MN-44 or MN-43's Done status — cosmetic replay-only artifact, not a functional session break. Proposed direction for whoever picks it up: store resize events as markers inside `history.log` itself (not just call `proc.setwinsize`), replay them in original order so the terminal's width tracks what it was at write-time for each segment, rather than replaying the entire buffer at one fixed current width.

## MN-45 — multiagent capability, real design round + 3 phases, all committed

The least-defined ticket in the epic (`docs/Agents-v1-scope.md` §5 explicitly said "no architecture yet") got a genuine `planner` design round rather than just phasing an existing spec.

**Key discovery that shaped everything**: Claude Code CLI itself (v2.1.251) exposes `--mcp-config`/`--settings` flags (additive, verified live to NOT touch a folder's own `.mcp.json`/`.claude/settings.json`) and `SubagentStart`/`SubagentStop` hook events with `"type": "http"` (CC's own process POSTs a JSON body, `agent_id` stable across the pair). This is CC's own sanctioned side channel, entirely orthogonal to the raw PTY byte stream `agent_runtime.py` (MN-43) deliberately never parses — it's what let MN-45 add real agent-to-agent coordination and subagent visibility WITHOUT reopening the "should the console parse structured events" question MN-43/44 already closed.

- **Phase 45a (`ac8170f`)**: a third MCP face, `/mcp-agents`, gated by a new per-session token (minted at spawn, in-memory only, matching `_sessions`' own no-restart-adoption stance). `src/mcp_agents.py`: `list_sessions`/`send_message`/`read_recent`/`session_summary`/`interrupt` (soft Escape only, not a process kill). `send_message`'s `[from <slug>·<chat>]` prefix is always server-derived from the resolved token, never a caller argument — the anti-spoofing property the whole design leans on. **Every tool call is audited to a new `servicelog.agent_events` table** — this was the lead's own explicit, non-negotiable addition: machine-wide reach (any live session can message/interrupt/read any other live session, including ones on a less-trusted custom-proxy backend) was accepted as consistent with mnemo's existing single-user/no-inter-principal-isolation trust model, but ONLY made auditable, not narrowed. **The one required review fix**: `resolve_session_token` initially used a plain `dict.get()` — not constant-time. This codebase already has an explicit, twice-repeated pattern for this (`registry.resolve_by_token` for bank tokens, `api._token_ok` for the service token, both do a linear scan with `secrets.compare_digest` specifically because a dict lookup isn't constant-time) — session tokens were the one new credential kind that broke the pattern. Fixed to match. **Verified live with exactly 1 real spawn ($0.53)** — both CLI mechanisms confirmed to work exactly as hoped, no redesign needed.
- **Phase 45b (`90aa302`)**: subagent-run visibility without ever parsing PTY output. Hook events persist verbatim (nothing filtered/reshaped — the safety net behind an accepted gap, see below) to a `subagents.jsonl` sidecar per chat, broadcast over the chat's EXISTING WS channel as a new `subagent_event` envelope (no second socket). Frontend `SubagentPanel.tsx` says "started — no completion signal yet" / "done", deliberately never "running" — there's no way to distinguish a crashed subagent (Start with no eventual Stop) from a genuinely still-running one, and the UI copy doesn't pretend otherwise. **Review fix**: the broadcast half of `record_subagent_event` wasn't exception-guarded despite the docstring promising "persistence or broadcast failure is logged and swallowed, never raised" — only the persist half actually was. Fixed to guard both independently. **Accepted gap, not chased further**: the real field names inside `SubagentStart`/`SubagentStop` hook JSON (beyond `agent_id`/`hook_event_name`) were never captured to a persisted file from 45a's gate spike (only printed to a console nobody saved) — frontend field-name guesses for `agent_type`/`last_assistant_message` are unverified. Decided NOT to spend another real spawn chasing this: since the raw payload is stored/broadcast verbatim, no data is lost, only cosmetic display fallback risk until corrected by observation.
- **Phase 45c (`868e24f`)**: `POST /api/agents/{slug}/subagents/{name}/launch` turns a `.claude/agents/*.md` definition into a genuinely new, independent, top-level `agent_registry.Agent` — the exact same `create()` path (root omitted, `owns_root=True`) a normal user-initiated creation uses, not a lightweight/nested shortcut, per the lead's explicit decision. Reuses MN-44's own frontmatter regex and `create()`'s existing `unique_slug()` collision handling rather than duplicating either. **Terminology decision worth remembering**: the button says "Перетворити на агента"/"Turn into agent," NOT "Запустити"/"Launch" — deliberately avoiding overloading the same word for two different concepts in the same feature area (MN-45b's "Subagent runs" is about *observed hook events during a live session*, this is about *turning a definition into a standalone persona*). When two features in the same area could both reach for the same natural word, check whether they mean the same thing before reusing it.

**Pattern worth remembering across all 3 phases**: every review found real, narrow, fixable gaps (a missing constant-time comparison, an unguarded exception path) rather than either "nothing wrong" or "fundamentally broken" — consistent with this project's whole day's experience that independent review earns its cost even when an implementer's own testing was already thorough. All 3 phases used a total of exactly 1 real `claude` spawn for the entire ticket (45a's gate verification) — 45b and 45c needed zero real spawns, matching the plan's own "sparse real-spawn" discipline throughout.
