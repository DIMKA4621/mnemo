# 2026-08-20 (десяте) — третій "застиглий self-reference" баг у self-update

Знайдено service-dev під час live-доказу для кроку 9, зупинено й ескальовано координатору замість мовчазного патчу чужого файлу — правильно, `service_ctl.py` не його територія.

## Баг

`service_ctl.start()` спавнить сервер як `subprocess.Popen(argv, cwd=engine_root, ...)`, де `engine_root = Path(__file__).resolve().parent.parent` — **безумовно**, незалежно від того, чи переданий явний `target`.
`target_for_version(version_dir)` (фікс кроку 8) підміняє лише інтерпретатор в `argv[0]`, **не чіпає `cwd`**.

**Доведено мінімальним експериментом:** `cwd` переважає `PYTHONPATH` для резолюції модуля при `-m` — безумовно (два фейкові дерева `fakeA`/`fakeB`, той самий інтерпретатор, `-m src.probe` завжди резолвить із `cwd`, не з `PYTHONPATH`).

**Наслідок для `_cmd_update_apply`:** ця команда виконується **всередині** процесу, диспетчованого під **старою** версією — `cwd` цього процесу зафіксований на старій версії на весь його час життя.
Коли він кличе `service_ctl.start(target=target_for_version(new_dir))` — новий процес отримує **новий** інтерпретатор, але **старий** `cwd` від батька.
`-m src.cli` резолвиться проти **старого** `src/` дерева.
Залежності оновлюються (новий venv, нові site-packages), **код застосунку — мовчки ні**.

**Чому крок 8 це не спіймав:** тестовий риг білдив `v-old` і `v-new` з **того самого** чекауту в тому самому прогоні — байт-у-байт однаковий код.
Баг дає нульову спостережувану різницю, коли старий і новий код ідентичні — саме та умова, в якій крок 8 тестувався.
"Доктор підтверджує сервінг під новою venv" перевіряло **інтерпретатор** (який `target_for_version` і справді фіксує) — не перевіряло, **яке дерево коду** реально виконується, бо не було способу їх розрізнити за однакового коду.

## Патерн, вартий уваги сам по собі

Це **третій** баг такого класу на цій фічі: (1) `sys.prefix`/`sys.executable`/ `__file__` у лаунчері прив'язані до venv часу білда exe, не місця запуску (крок 0); (2) `service_ctl.start()` без явного target брав застиглий `sys.executable` виклику (крок 8); (3) цей — `cwd` для spawn береться з місця, де лежить **поточний** `service_ctl.py`, не з target.
Усі три — одна й та сама помилка в різних масках: **код, написаний для світу з одним статичним venv, тихо припускає "я і є той venv/той код", коли фіча прямо робить цю умову хибною.** Кожен новий модуль, що торкається self-update, має явно питати "а що, як я виконуюсь не з тієї версії, яку щойно перемкнули" — а не вважати самоочевидним.

## Статус — виправлено й доведено тим самим днем

`target_for_version(version_dir)` тепер повертає `SpawnTarget(argv, cwd)` — `cwd` рахується там же, де й шлях інтерпретатора.
`service_ctl.start()` отримав параметр `cwd` (і `restart()` пробрасує його), **дефолтна поведінка без `cwd` не змінилась** — і досі `Path(__file__).resolve() .parent.parent`, тож жоден наявний викликач (shell, інсталятор, `test_service_ctl.py`'s наявні тести) не зачеплений.
`_cmd_update_apply()`'s обидва виклики `start()` (forward і rollback) тепер розпаковують `SpawnTarget` і передають `cwd` явно.

**Перевірено з реально різним кодом** (урок цього ж багу — попередній тест кроку 8 пропустив саме тому, що код був однаковий): `v-old`/`v-new` зібрані з того самого чекауту, потім **вручну відредаговано** кожен build's власний `src/config.py` (маркер у `SERVICE_VERSION`, `OLD` vs `NEW`, підтверджено SHA-256, що дерева тепер справді різні).
Маркер проходить через `api.py`'s `_write_service_info()` у `service.json.version`, записуваний **реальним процесом, що виконується** — найпряміший доступний доказ, яке дерево коду реально запущене, не лише який інтерпретатор.

- **Forward apply:** `service.json.version` `OLD` → `NEW` після `update-apply`, `python`-поле теж коректно вказує на venv нової версії.
- **Forced rollback (регресія кроку 8):** venv нової версії знову зламано → `update-apply` відкотив → `service.json.version` повернувся на `OLD`, `python` — на venv старої версії, сервіс живий.
  І інтерпретатор, і код відкотились разом.

Повна суїта: **89 passed, 0 failed**, без регресій від зміни сигнатури `start()`.
Реальний рушій/сервіс — не чіпались.

Готово для service-dev — крок 9's live-доказ реального перемикання коду (не лише venv) тепер розблокований.
