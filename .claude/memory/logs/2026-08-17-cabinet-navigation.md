# 2026-08-17 — глобальна навігація кабінету й окремий журнал

Після аудиту живої сторінки узгоджено інформаційну архітектуру наступного
кроку. Код не змінювався.

## Що показав аудит

На вікні 1278×944 нижній журнал постійно займав 240 px; на 1000×800 і
760×800 — 220 px при лише 521 px робочої висоти. На вузькій ширині Memory
складався вертикально, а журнал лишався прикріпленим, тому документ ішов далеко
нижче видимої області. Settings візуально заміщав Memory, але технічно лишався
fixed overlay: Memory продовжував жити під ним у DOM та accessibility tree.

Внутрішню модель Memory (`Банки → Файли → Вміст`), меню дій банку `···` і
внутрішню ліву навігацію Settings визнано правильними — змінюється оболонка,
не ці робочі моделі.

## Узгоджені рішення

- Глобальний компактний rail — **ліворуч**.
- Перші top-level сторінки: **Памʼять / Журнал / Налаштування**.
- Агенти не показуються до появи реальної сторінки; потім додаються четвертим
  пунктом.
- Settings стає route/page, а не fixed overlay.
- Нижній dock журналу прибирається з Memory повністю.
- Журнал стає окремою master-detail сторінкою: події ліворуч, повні деталі
  вибраної події праворуч; вкладки `Запити` / `Індексація`, фільтри за банком,
  часом і статусом, `N із total`.
- Query detail показує вхід і результати в тому порядку, як їх отримав агент;
  результат веде кнопкою «Відкрити в Памʼяті» до банку, файла й чанка.
- У service journal надалі зберігається **точний snapshot `content` кожного
  повернутого hit**. Поточні locator-и недостатні: перечитати текст пізніше з
  індексу означає показати нову редакцію як стару відповідь. Більший розмір
  `service.db` прийнято як ціну історичної чесності; база локальна, ротована й
  обмежена retention/row cap.

Повне пояснення лишено в `topics/cabinet-ui.md`.
