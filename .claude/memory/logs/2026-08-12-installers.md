# 2026-08-12 (пʼяте) — POSIX-інсталятор нарешті виконується

Коміт: `test(install): run the POSIX installer pair for real in CI`.

## Що було не так

CI ганяв чотири конфігурації, але **установку виконував лише на Windows**.
Кроки на всіх платформах: залежності ставилися **в раннер**
(`pip install -r requirements.txt`), далі `test_platform.py` (проводка,
плани `init`, збіг двох `mcp-setup.*`) і `test_pipeline.py` (`.md → чанки →
вектори → пошук`). І тільки на Windows — `test_install_windows.py`, який
справді ставить рушій у тимчасовий `-InstallHome` і зносить його.

Тобто `install.sh` і `uninstall.sh` **не виконував ніхто й ніде**: ні CI, ні
розробник (локальна машина — Windows). Вони їхали в git на підставі
прочитання, а логи 2026-08-10 це чесно фіксували («`install.sh` лише
синтаксично перевірено»). Цей запис закриває ту дірку.

## Знайдено ще до першого прогону

**`uninstall.sh` мав режим `100644`** — без біта виконання. Задокументоване
`./uninstall.sh` на Linux/macOS впало б на першому ж рядку з `Permission
denied`. `install.sh` — `100755`, тож дефект був рівно в одному з двох і в
diff невидимий: режим не показується в тексті змін.

Виправлено `git update-index --chmod=+x`, і тепер це **перевірка**, а не
разова правка: `test_install_posix.py` починається з `os.access(X_OK)` на
обидва скрипти.

## `tests/test_install_posix.py`

Дзеркало Windows-суїти, той самий сценарій, усе в тимчасовому `--home`
(`рушій з пробілами` — пробіли + кирилиця):

`--help` і невідомий прапорець (exit 2) → `--check` на **неіснуючому** home
→ установка → лаунчер виконуваний і не піддається затіненню проєктним
`src/` → **модель не качається, служба не стартує** → `--check` каже
`sqlite-vec loadable` → реінстал береже `state/` і `model-cache/` →
`--deps-only` не дзеркалить `src/` → апгрейд з v2 (три `.db` без
`banks.json` → `clean-orphans`, разом із `-wal`) → **повний інстал таки
стирає чужий файл із `src/`** (дзеркало, не злиття) → `--dry-run` →
відмова без термінала й без `--yes` → `--keep-model --keep-state` →
повне знесення → двічі не помилка.

Дві речі, яких немає у Windows-версії:

- **`sqlite-vec loadable` як окрема асерція** — це рівно те питання, чия
  відсутність пропустила непрацездатну macOS-збірку (див.
  `2026-08-12-pipeline.md`). Тепер його ставить і сам інсталятор, і тест.
- **дзеркальність `src/`**: файл, який лишив `--deps-only`, мусить зникнути
  після повного інсталу. `rsync --delete` і запасна гілка `cp` мають про це
  домовитися, а гілок дві саме тому, що `rsync` є не скрізь.

`user_scope()` знімає **до/після**: дайджести `~/.profile`, `~/.bashrc`,
systemd-юніта й launchd-плісту. Не «їх немає» — на машині з живим рушієм
вони законно є, — а «незмінні». Це і є те, що дозволяє ганяти суїту на
робочій машині.

Парсер звітів ріже рядок за **фіксованою шириною** (`%-13s` в
`install.sh`, `%-15s` в `uninstall.sh`), а не вгадує кількість пробілів;
звірено з реальним виводом `printf`.

## Чого перевірити локально не вийшло

Нічого з цього. Машина — Windows, а `install.sh` кладе venv у `.venv/bin`,
якого під Git Bash не існує (там `Scripts`). Локально зроблено лише те, що
можна чесно зробити: `bash -n` на обох скриптах, компіляція тесту й звірка
парсера з `printf`. **Єдиний справжній доказ — прогін CI**, і саме тому цей
крок і додається.
