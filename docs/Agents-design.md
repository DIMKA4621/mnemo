# mnemo — сторінка «Агенти»: керовані персони поверх кабінету (концепт)

> **Статус:** рання концепція, вироблена в діалозі 2026-08-20, **ще не
> імплементаційна**. Нічого з цього не зачіпає й не змінює жодне з locked-рішень
> `Memory-design-v3.md` — це надбудова над кабінетом, нова верхньорівнева область,
> паралельна «Памʼяті», а не її частина. Формального implementation/contracts
> доку для цієї фічі поки нема — цей файл лише фіксує домовлене, щоб було з чого
> починати планування фазами, коли дійдемо.

## 0. Навіщо

Сьогодні один банк памʼяті = одна тека `.md`, і нею користується будь-який агент, що на неї вказує (`.mcp.json`). «Агенти» — про інше: не памʼять сама по собі, а **керована персона** — імʼя, свій `CLAUDE.md`, свій набір MCP/скілів/ рулів, своя памʼять і свій чат — з якою можна розмовляти прямо з кабінету, а не лише через CLI-сесію Claude Code.
Мотивація користувача: керувати кількома персонами з різними інструкціями/бекендами з одного місця, не тримаючи це руками по різних проєктних теках.

Памʼять агента — не нова сутність: це просто ще один банк, автоматично зареєстрований при створенні агента.
Уся інфраструктура (реєстр, індексація, watcher, пошук) переноситься as-is, нового руху даних тут нема.

## 1. Тека агента — той самий патерн, що й банк

Довільний корінь на диску з дефолтом, а не або/або:

- дефолт: `~/.mnemo/agents/<slug>/` (engine home, поруч зі `state/`, `model-cache/`);
- при створенні можна одразу вказати іншу теку (той самий file-picker, що вже є для «додати банк») — корінь обирається один раз, не переїжджає пізніше.

Усередині:

```
agents/<slug>/
  CLAUDE.md
  launch.json        ← бекенд/запуск цього агента (розділ 3)
  .claude/rules/*.md  ← імпортовано з реєстру
  .claude/skills/*    ← імпортовано з реєстру
  .mcp.json           ← зібраний з обраних MCP-серверів
  memory/              ← авто-зареєстрований окремий банк
```

`memory/` реєструється як банк автоматично при створенні агента — той самий виклик, що й ручне «додати банк» у кабінеті, лише без діалогу.

## 2. Створення агента — два кроки

Майстер, не одна форма:

1. **Імʼя + `CLAUDE.md`** — вебредактор (textarea/CodeMirror), зберігає безпосередньо у файл.
2. **Бекенд запуску** — розділ 3 нижче.

MCP/скіли/руси — **поза майстром**, окремою вкладкою «Реєстр» (розділ 4), яку проходять після створення, коли агент уже існує.

## 3. Бекенд запуску — per-agent, не машинний

Ключове уточнення від користувача: це **не** машинне налаштування (не поле в ⚙), а другий крок майстра створення **кожного окремого агента**.
Один агент ганяє через один проксі, другий — через інший, третій — на дефолтах, незалежно.

Той самий принцип, що вже є на екрані ембеддингів — **пресет, обирають, а не набирають**:

- **«Стандартний»** — дефолти Claude Code CLI/SDK, нічого не вказувати;
- **«Кастомний»** — хост, порт, модель, поріг autocompact, довільні extra-параметри запуску (одне текстове поле для «сирих» прапорців).

Зберігається в `agents/<slug>/launch.json`, не в машинних `settings.json`:

```json
{"mode": "standard"}
{"mode": "custom", "host": "...", "port": ..., "model": "...", "autocompact": ..., "extra_args": "..."}
```

## 4. Реєстр — одна вкладка, три секції

MCP / Skills / Rules **не** три окремі вкладки — одна, з трьома секціями чекбоксів.
Джерело:

- user-scope (`~/.claude.json` → MCP-сервери, `~/.claude/skills/`, `~/.claude/rules/`), або
- довільна тека (кнопка «сканувати теку» — знаходить `.mcp.json`/`mcp.json`, `skills/`, `rules/` всередині, той самий патерн, що пошук банку по теці).

Кожен знайдений рядок — чекбокс + вибір агента(ів)-цілей.
Імпорт = **копіювання** у теку агента (`.mcp.json` мерджиться, файли скілів/рулів копіюються), не symlink і не посилання на оригінал — агент лишається самодостатньою текою.

## 5. Навігація

Два різні рівні, які на початку розмови зливались — важливо тримати окремо:

- **Глобальний сайдбар** (`.sidebar`, `shell.js`, `index.html:28-49`) — сьогодні три фіксовані маршрути-кнопки (`Памʼять` / `Журнал` / `Налаштування`), нічого не розгортається.
  Стає **чотирма**: `Памʼять` / **`Агенти`** / `Журнал` / `Налаштування`.
  Ще одна кнопка-іконка, не дерево.
- **Сторінка «Агенти»** (нова, за зразком `page-memory.js`) — власна in-page ліва панель, дерево з розгортанням:

  ```
  АГЕНТИ                       [＋ Додати агента]   ← в шапці панелі,
  ▾ Агент №1                                          дзеркалить
      • Чат «дебаг API»                                «＋ Додати банк»
      • Чат «планування релізу»                        (page-memory.js:76-77)
      Показати ще…
  ▸ Агент №2
  ▸ Агент №3
  ```

  Стрілочка розгортає агента → чати підрядками, прямо в панелі (не окремою колонкою).
  Каповано (5–10 останніх, точне число — деталь білда), «показати ще» коли більше.
  Клік по чату відкриває його в основній робочій області.

## 6. Чат-рантайм — головне архітектурне рішення

Вимога користувача: перемикання вкладок/агентів **не** обриває процес мислення агента, який щось генерує.
Розвʼязок — той самий принцип, що вже тримає всю систему: **живий процес належить бекенду, не браузеру**.

- кожен активний чат = сесія Claude Agent SDK, яку тримає **сервіс** (FastAPI-процес), не вкладка браузера;
- новий бекенд-компонент, умовно `agent_runtime.py` — менеджер живих SDK-сесій, ключованих `chat_id`, прямий аналог того, як уже влаштовані `workqueue`/`watcher` (фонові, резидентні, UI лише підглядає);
- стрім думання йде через WebSocket; будь-яка кількість підключених клієнтів підписується/відписується від того самого стріму, не зупиняючи генерацію (закрив вкладку — процес далі працює, повернувся — доганяєш буфер);
- історія повідомлень пишеться на диск у теці чату — реконект після довгої відсутності підхоплює лог, а не губить.

UI-паритет із консоллю Claude Code — вибір моделі, слеш-команди, вкладення зображень — деталь фази 5, не архітектурне рішення.

**Не вирішено, лишається на фазу білда:** скільки одночасно активних (реально «думаючих») SDK-сесій тримати — жива сесія коштує ресурсів, тримає з'єднання; питання ліміту/черги свідомо відкладене.

## 7. Фазування (чернетка)

1. Реєстр агентів + storage — авто-створення теки, авто-банк памʼяті, без UI.
2. Сторінка «Агенти»: дерево (список + розгортання), майстер створення (крок 1 — імʼя+CLAUDE.md, крок 2 — бекенд).
3. Вкладка «Реєстр» (MCP/Skills/Rules — сканування + імпорт).
4. `agent_runtime.py`: живі SDK-сесії, WS-стрім, збереження історії.
5. UI чату (паритет із Claude Code console).
6. Обмеження одночасності (розділ 6, відкрите питання).

## 8. Рішення, зафіксовані в розмові

1. Тека агента: дефолт (`~/.mnemo/agents/<slug>/`) + можливість вказати іншу при створенні — не «завжди питати» і не «один спільний батьківський корінь у налаштуваннях».
2. `memory/` теки агента — звичайний банк, авто-реєстрований, без нової інфраструктури.
3. Створення агента — два кроки (імʼя+CLAUDE.md, потім бекенд); MCP/скіли/руси — поза майстром.
4. Бекенд запуску — **per-agent** (`launch.json` у теці агента), не машинне налаштування; пресет «стандартний/кастомний», той самий принцип, що на екрані ембеддингів.
5. Реєстр MCP/Skills/Rules — одна вкладка з трьома секціями, не три окремі; імпорт копіюванням у теку агента.
6. Глобальний сайдбар — плоский, стає 4 маршрутами; розгортання агент→чати живе **всередині** сторінки «Агенти», не в глобальному сайдбарі.
7. «＋ Додати агента» — в шапці in-page панелі, дзеркалить розміщення «＋ Додати банк» у Памʼяті.
8. Чат-рантайм — бекенд-резидентні SDK-сесії, WS multi-subscriber, персистентна історія на диску; перемикання клієнта не спиняє генерацію.

## 9. Відкрито (не вирішено)

- Ліміт одночасних активних SDK-сесій (розділ 6).
- Точне число «останніх N чатів» перед «показати ще» (5 чи 10).
- Чи агентська `memory/` показується і в самій сторінці «Памʼять» як звичайний банк, чи ховається звідти (вона й так технічно банк — питання лише видимості в UI).
- UI-паритет чату (слеш-команди, вибір моделі, вкладення) — список конкретних можливостей ще не складений.
