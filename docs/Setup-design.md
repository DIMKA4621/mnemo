> автозапуску) — тут не описано нічого, чого ще немає, як наявного.

## Підключення проєкту

Основний принцип — підключення виконує Claude Code за визначеною процедурою: детерміновані кроки виконуються скриптами; зміни в уже наявних файлах проєкту — з показом і підтвердженням користувача. Кроки крос-платформні (Linux / macOS / Windows).

## Рівень системи

Основний принцип — рушій (середовище виконання, ембединг-модель, векторний індекс) встановлюється одноразово в домашній директорії користувача, спільний для всіх проєктів, оновлюється незалежно від них.

* Точка входу рушія — лише для автоматизації (хуки, MCP, інсталяційний скіл), не для людини напряму.
  **З фази 5 частина команд стає людськими** — `service start|stop|status|restart`,
  `doctor`, `ui` (FR-9); решта лишається машинною.
* Модель завантажується тільки за явною згодою, ніколи неявно. Інсталятор
  **питає** `[Y/n]`, коли кеш порожній — згода лишається явною, просто
  трапляється в тому ж сеансі. Неінтерактивний запуск (CI, юніт, пайп)
  **ніколи не питає**: пропускає й друкує команду, бо запит, якого ніхто не
  бачить, або висне назавжди, або прочитає байт чужих даних як відповідь.
  Прапорці `--model` / `--no-model` (`-Model` / `-NoModel`) — для скриптів.
* Індекс — локальний, одноразовий, відтворюваний, не в git. Ключується **коренем
  банку**; індекси з-під v2, ключовані коренем проєкту, осиротіють і **не
  видаляються автоматично** — прибирання лишається явним (майбутній
  `mnemo doctor` їх покаже й прибере на команду).
* **З фази 5** інсталятор також реєструє автозапуск сервісу (Task Scheduler /
  `systemd --user`), і сам робить `stop → refresh → start`: піднятий бекенд
  тримає `python` у `.venv`. **Руками зупиняти сервіс перед оновленням не
  треба** — інсталятор знімає його сам і піднімає назад.
* **Інсталятор — це вся машинна частина, однією командою.** Після venv,
  залежностей, лаунчера, токена, профілю й автозапуску він доводить справу
  до кінця: модель (за згодою), `service start` **навіть якщо нічого не
  працювало** (реєструвати автозапуск і лишити сервіс лежати до наступного
  логона — це напівінсталяція, яка читається як «не працює»), і наприкінці
  `doctor`, чий вивід і є останнім на екрані. Кінець на **доказі, а не на
  обіцянці**. Прапорці `--no-start` / `-NoStart` лишають старий шлях.
* **Ізольований `--home` / `-InstallHome` не отримує нічого з цього** — ні
  моделі, ні старту сервісу, ні `doctor`, ні токена, профілю й автозапуску.
  Це ручна або тестова копія, і саме тестова копія є причиною: 2.2 ГБ
  завантаження, другий процес на порту 8918 чи `doctor` про *справжній*
  рушій — це тест, що поліз чіпати машину.

## Рівень проєкту

Основний принцип — усе, що потрібно проєкту для роботи з памʼяттю, лежить у
самому проєкті й успадковується кожним, хто його клонує. **Фаза 4 зробила з
цього рівно один виняток, і він навмисний**: обліковка (токен банку) — річ
машинна й секретна, тож у git її немає. Клонувальник бере свій токен із
кабінету (`mnemo ui`); усе інше — правило, скелет памʼяті, шаблон wiring —
приїжджає з репозиторієм.

* Реєстрація банку та MCP-інструмента памʼяті: `mnemo init` реєструє корінь
  памʼяті проєкту як банк, отримує його токен і вписує в MCP-запис.
* Хуки: **їх немає взагалі** (рішення #27). Фаза 4 прибрала їх із типового
  `init` і лишила два засіви за прапорцями; тепер немає й засівів — ані
  `--with-memory-hook`, ані `--with-inject-hook`, ані самих команд.
  Реіндекс робить watcher (рішення #15), а памʼять дістають **пошуком, не
  інʼєкцією**: інʼєкція віддає її до того, як задачу сформульовано, і це
  читається як «памʼять уже зібрано». Мапу розкладки дає тул `tree` на
  вимогу, тож і той засів став зайвим. Дисципліну несе
  `.claude/rules/mnemo-memory.md` — **одне місце**, бо два механізми, що
  кажуть одне й те саме, це два механізми, які можуть розійтися.
  `--migrate` знімає всі хуки, які mnemo колись писала.
* Скелет памʼяті: тонкий індекс + директорія логів + topic-файли. Поділу на
  агентні блоки **більше немає**: банк плаский, розділення — окремі банки
  (рішення #13).
* Виклики у git-tracked налаштуваннях — портативні, без машинно-залежних шляхів.
  **Фаза 4 змінила тут головне: MCP-запис більше не git-tracked.** У ньому
  стоїть власний токен банку, літеральний, — тож `.mcp.json` став
  згенерованим і git-ignored (рядок у `.gitignore` дописує сам `init`; якщо
  файл уже під git, `init` **відмовляється**, нічого не пише й друкує
  `git rm --cached .mcp.json`). Проєкт із конвенцією шаблонів тримає в git
  `.mcp.json.template`, `.mcp.env.example` і `mcp-setup.sh` із плейсхолдерами,
  а значення — у git-ignored `.mcp.env`. Саме правило не змінилося — у git не
  потрапляє ні машинозалежний шлях, ні секрет, — змінилося лише те, який файл
  його несе.

## Крос-платформність

Основний принцип — один і той самий проєкт і той самий git-tracked wiring
працюють на Linux, macOS і нативному Windows; відмінності інкапсульовані в
інсталяторі рушія й у способі, у який ОС резолвить портативний шлях.

* Інсталятор рушія — платформозалежний, контракт однаковий: `install.sh` на
  POSIX; `install.ps1` на нативному Windows (вбудований PowerShell 5.1+,
  64-бітний Python 3.10+; без WSL, PowerShell 7 чи запису в PATH). Параметри
  Windows-інсталятора: `-Check`, `-InstallHome`, `-Python`; типовий і
  канонічний дім рушія — `%USERPROFILE%\.claude\mnemo`. `-InstallHome`
  призначений для ізольованих перевірок або ручних запусків: portable project
  wiring завжди звертається до канонічного дому.
* Точка входу рушія — один логічний шлях `~/.claude/mnemo/bin/mnemo`: на POSIX
  це безрозширенний Bash-лаунчер, на Windows — справжній `bin\mnemo.exe` (ОС
  сама дорезолвлює безрозширенний шлях до `.exe`).
* Портативний wiring без машинних шляхів. Хуків у ньому більше немає взагалі
  (рішення #27), тож лишився один файл — `.mcp.json`.
  **stdio-форма `.mcp.json` пішла у фазі 4**: MCP — це HTTP до
  вже піднятого сервісу, `{"type": "http", "url":
  "http://127.0.0.1:<port>/mcp?token=<токен банку>"}`. Ні `command`, ні
  `args`, ні `headers`, ні сегмента шляху, ні назви банку: **адресою є сам
  токен** — він належить одному банку й резолвиться в нього, тож будь-що інше,
  що називає банк, могло б лише суперечити обліковці, а запит, який успішно
  влучив не в той банк, виглядає цілком нормальним. `X-Mnemo-Bank` зник саме
  через це. Токен без плейсхолдера — причина, чому цей один файл git-ignored;
  у шаблонному проєкті в git лишаються `{{MNEMO_PORT}}` / `{{MNEMO_TOKEN}}`.
  Точна форма — `Memory-contracts-v3.md` §10.4; розпізнавання й переписування
  старих форм (stdio, а також `/mcp/<bank>?token=…`, який тепер відповідає 400)
  — `mnemo init --migrate` (§11.3).
* Windows-інсталятор задає користувацьку змінну `HOME` лише якщо її ще немає
  (щоб `${HOME}` резолвився), ніколи не перезаписує її та відмовляється
  продовжувати, якщо вона відрізняється від PowerShell `$HOME`/`%USERPROFILE%`:
  і MCP, і hooks мають вказувати на один дім. Після першого створення `HOME`
  треба закрити й знову відкрити термінал або IDE, з якого запускається Claude
  Code, а потім перезапустити Claude Code.
* Визначення кореня проєкту в рантаймі — однакове всюди: явний `--root` >
  `MNEMO_ROOT` > `CLAUDE_PROJECT_DIR` > поточна директорія; відносні
  ідентифікатори проіндексованих файлів завжди використовують `/`, тому вони
  не розходяться між платформами лише через різні роздільники шляхів.
* Модель, як і раніше, завантажується лише явним прогрівом (`warmup`, ~2.2 ГБ),
  ніколи неявно — на всіх платформах.
