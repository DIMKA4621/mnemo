# mnemo як сервіс семантичної памʼяті: сховища `.md` + векторний рушій (v3)

> **Статус:** зафіксована **цільова архітектура на заміну v2** — не паралельна
> гілка, а повноцінне наступне ядро. v2 — поточний реалізований стан і працює як
> є, доки v3 не реалізовано. Нічого з v3 не «скасовує» v2 мовчки — усе, що v3
> інвертує проти v2, названо явно (розділ 1); стан рішень — у розділі 13.
>
> **Ключова зміна проти v2:** v2 — це «локальне, одноразове, без сервера/демона/
> Docker, їде з `git clone`». v3 — це **постійний локальний сервіс**, який володіє
> моделлю та індексом, **сам стежить за файлами** й віддає памʼять через кілька
> облич (MCP / HTTP / CLI / Web UI). Ми свідомо міняємо «немає демона» на «демон —
> це і є суть», бо саме відсутність демона породжує головний біль: холодний старт
> моделі й переіндексацію, що вішає сесію.
>
> **Перша версія — нативна, без Docker** (просто Python-сервіс у системі). Docker —
> пізніша опція й не привʼязаний до WSL2 (розділ 9).

---

## 0. Дві незмінні аксіоми (те, заради чого все існує)

Уся система тримається на двох речах, і тільки на них:

1. **Є `.md`-файли** — у довільно вкладених теках, довільної структури. Це
   **єдине джерело правди**. Їх редагує людина, агент або (в майбутньому)
   зовнішній інструмент. Ніщо інше не є першоджерелом.
2. **Є векторне сховище** — похідне від цих файлів, по якому на запит повертаються
   релевантні секції. Воно **одноразове й повністю відтворюване** з `.md`.

Усе інше в цьому документі — це лише машинерія, що надійно й автономно тримає
звʼязок `(1) → (2)` і дає до нього зручний доступ. Якщо колись доведеться
викинути пів системи — ці дві аксіоми лишаються.

## 1. Зсув парадигми: v2 → v3

| Аспект | v2 (чинний) | v3 (цей концепт) |
|---|---|---|
| Модель виконання | без демона; хук спавнить CLI щоразу | **постійний сервіс-демон**, завжди теплий |
| Тригер переіндексації | хуки (start / post-edit) | **watcher** стежить за файлами сам; для реіндексу хуки не потрібні |
| Модель ембедингу | локальний резидент, підіймається за потреби | той самий резидент, але **завжди теплий**, окремий нативний Python-процес, плагований провайдер |
| Область памʼяті | проєкт + внутрішні скоупи (`.claude/memory/` + `agent-memory/<agent>`) | **довільні «банки»** (теки будь-де); **без внутрішніх скоупів** — банк плаский; уся памʼять банку вкладена в **один** корінь (рішення #18) |
| Доступ | MCP + CLI + хуки | **MCP** (основний) + `/mcp-tools` (дзеркало для людини) + CLI + **Web UI**; `/api` приватний; хуки — насіння, автоматично не додаються |
| Мережа назовні | нічого | локальний HTTP + UI (loopback за замовчуванням) |
| Docker | **антипатерн, не вводимо** | **нативно, без Docker** у v1; Docker — пізніша опція, не WSL2-bound |
| Джерело правди | `.md` у git проєкту | `.md` **на місці** в будь-якій теці; git — за наявності місця (розділ 8) |

**Що лишається без змін** (переносимо з v2 as-is, це доведено робоче ядро):

* Однонаправлений sync `.md → індекс`. Індекс **ніколи** не редагується напряму.
* Hash-diff + **prune** (видалене з файлів зникає з індексу).
* Детермінований стабільний id чанка (однаковий на всіх машинах).
* Векторний пошук — **основний**; FTS5/BM25 — **вторинний**; злиття через RRF.
* Модель тягнеться **тільки явним warmup**, ніколи неявно.
* Один SQLite-файл на банк: вектори + FTS + стан (хеші) разом.

## 2. Модель даних: сховища («банки»)

> Термінологія: **сховище = база знань = банк** — це те саме. Далі — «банк».

**Основний принцип** — памʼять організована у **банки**. Банк — це **одна коренева
тека будь-де на диску** з довільно вкладеними `.md`-файлами довільної структури.
Один банк = одна база знань. Банків багато, вони незалежні, кожен має власний
похідний індекс.

* **Корені розкидані по системі.** Один банк — це папка проєкту тут, другий —
  папка проєкту там, третій — просто тека нотаток десь на диску. Сервіс **не
  вимагає**, щоб вони жили в одному місці: він тримає **реєстр коренів** (список
  тек-банків будь-де) й індексує кожен **на місці**. Саме цей сценарій — розкидані
  корені — робить нативний процес зручнішим за контейнер (розділ 9).
* **Реєстр банків** — конфіг сервісу: `id`, людська назва, кореневий шлях,
  провайдер ембедингу (опційно per-bank), стан індексу. Реєстр — це конфіг
  сервісу, не частина жодного банку.
* **Де лежить банк — обидва варіанти рівноправні** (джерело правди завжди `.md`
  на місці, розділ 8):
  * **у git-проєкті** — тека всередині репозиторію (напр. `.claude/memory/`).
    Файли версіонуються самим проєктом і їдуть з `git clone`. Спадкоємець v2.
  * **окремі файли на диску** — просто дерево `.md` десь у системі, поза git.
    Не версіонується — і це нормально.

  Git-трекінг — це **властивість місця**, куди вказує банк, а не окремий «тип».
* **Майбутні джерела банку** — корінь може бути не лише локальною текою, а
  віддаленим джерелом через адаптер: пошарена Notion-сторінка, Google Drive тощо.
  Поки **відкладено** (розділ 11); базовий і єдиний випадок першої версії —
  локальні файли.
* **Структура всередині банку — довільна.** Ніякої обовʼязкової схеми: вкладені
  теки, `MEMORY.md`-індекс — за бажанням, а не за примусом. Одиниця памʼяті — це
  секція файлу (за заголовками), як у v2.
* **Банк плаский — жодних внутрішніх скоупів.** Немає поділу на «памʼять проєкту»
  й «памʼять агента»: вибрана тека цілком, з усіма вкладеннями, — **один великий
  індекс**. Це свідоме спрощення проти v2 (де були `project` / `agent` скоупи).
  **Потрібне розділення → окремі банки:** користувач розносить теки й дає кожній
  свій банк (напр. один банк = один агент), а доступ розводить окремими
  MCP-підключеннями (розділ 6). Ізоляція — на рівні банку, не всередині нього.
  «Плаский» стосується **ізоляції**, не навігації: звузити пошук до підтеки все
  одно можна — опційним `path_prefix` (шлях уже є в метаданих чанка), лише це
  зручність, а не межа доступу.
* **Індекс банку** — окремий SQLite-файл у стані сервісу, ключований хешем
  кореневого шляху банку (як у v2: `sha1(root)`). Файли — на місці, індекс —
  централізовано в стані сервісу.

**Дерево файлів як перший клас.** Мінімально сервіс віддає **навігаційне дерево**
банку (вкладеність + заголовки + внутрішні посилання між `.md`). Цього достатньо,
щоб «бачити структуру». Повноцінний **граф знань** (сутності/звʼязки) — це
можливий **пізніший, опційний** шар поверх дерева, а не вимога першої версії
(розділ 11). Не ускладнюємо там, де досить дерева.

## 3. Похідний індекс (переноситься з v2)

**Основний принцип** — на кожен банк один SQLite-файл, що тримає вектори + FTS +
хеші стану. Одноразовий, відтворюваний, gitignored.

Пайплайн запису лишається точно як у v2:

1. Обхід `.md` банку, sha256, порівняння зі станом у базі → додалося / змінилося / зникло.
2. Розбиття змінених файлів на чанки за заголовками (малий файл = один чанк).
3. Ембединг чанків через **провайдера** (розділ 4).
4. Запис чанків + векторів + метаданих (банк, шлях, стабільний id);
   **prune** того, чого вже немає у файлах.

Ідемпотентність, детермінізм, повна відтворюваність — незмінні властивості.

**Що нового проти v2:** цей пайплайн більше не запускається хуком «на льоту» в
межах 60-секундного бюджету. Його виконує **watcher** у фоні, без дедлайну
(розділ 5). Це прибирає єдину справжню причину зависання сесій.

## 4. Ембединг-провайдер (плагований) і як модель працює як сервіс

**Основний принцип** — ембединг схований за **інтерфейсом провайдера**
`тексти[] → вектори[]`. Ядро не знає, чим саме рахуються вектори.

* **`local`** (за замовчуванням) — наша ONNX-модель `multilingual-e5-large`,
  яку тримає **теплий резидент**. Це вже реалізований `embed-server`
  (loopback TCP, налаштовуваний bind/dial). У v3 idle-таймаут типово **`0`, що
  означає «немає виходу через простій»** — а не «висить завжди». Резидент
  так само **підіймається на першу потребу** і так само зникає, коли
  `mnemo service stop` прибирає бекенд разом із ним. Змінилось лише те, що він
  більше не вбиває себе за півгодини бездіяльності: старе значення `1800`
  коштувало ~9 с на першому ж пошуку після паузи.
* **`api`** — зовнішня embeddings-модель по API (напр. OpenAI/Cohere/локальний
  сумісний ендпоінт). Той самий інтерфейс, інша реалізація. Дає вибір
  «швидше/дешевше/без 2.2 ГБ локально» ціною зовнішньої залежності й приватності.
* **Провайдер — per-service або per-bank.** За замовчуванням один на сервіс;
  за потреби банк може перевизначити (напр. приватний банк — тільки `local`).
* **Інваріант розмірності.** Зміна провайдера/моделі змінює розмірність векторів →
  індекс банку **повністю перебудовується** (детермінований rebuild з `.md` це й
  так дозволяє). Провайдер фіксується в метаданих банку, щоб не змішати вектори
  різних моделей у одній базі.

**Як модель «запускається як сервіс» (нативно, без Docker).** Це найпростіша
частина, хоч і звучить складно:

1. **Один раз** явний `warmup` завантажує модель (~2.2 ГБ) у локальний кеш на
   диску. Більше вона нікуди не качається.
2. Далі легкий **процес-резидент** — звичайний Python-процес, не контейнер —
   вантажить модель у RAM **один раз** і слухає на loopback (`127.0.0.1`). Це вже
   існуючий `embed-server`.
3. Клієнти (watcher, MCP, CLI) моделі **не тримають** — вони шлють тексти
   резиденту й отримують назад вектори. Копія моделі в памʼяті — одна на машину.
4. Резидент сам керує життєвим циклом моделі: **підіймається на першу потребу**,
   далі тримає модель теплою (idle-вихід вимкнено, див. вище), перевіряє, що
   вона відповідає, і **перезапускається при потребі**. Живе рівно стільки,
   скільки сервіс: `mnemo service stop` знімає його разом із бекендом. З
   autostart-ом холодного старту після входу в систему практично немає.
5. **Смерть резидента не буває тихою.** Він може впасти нижче Python (segfault
   в ONNX) — тоді лишає нативний дамп у `~/.claude/mnemo/embed-crash.log`, а
   клієнт відрізняє «помер посеред запиту» від «недосяжний» і каже про перше
   вголос. Мовчазний фолбек у другу, in-process копію моделі — саме та відмова,
   яку ми більше не приймаємо.

Ніякого Docker для цього не треба: це просто Python-процес, що тримає модель і
відповідає по TCP на loopback. (Контейнерний варіант тієї самої ідеї —
*persistent-resident* профіль у `docs/containers/README.md` — лишається як
**пізніша опція** для Linux/серверів, розділ 9, а не як вимога.)

## 5. Демон-споглядач (watcher) — серце автономності

**Основний принцип** — сервіс **сам** помічає зміни у файлах банків і
переіндексовує у фоні. Це те, що перетворює mnemo з «плагіна, який треба
смикати» на «підключив і працює».

* **Стежить** за всіма зареєстрованими банками. Оскільки файли й демон — на одній
  (локальній) ФС, події ФС приходять надійно, без host↔container розривів.
* **Debounce + черга.** Пачка збережень одного файлу схлопується в одну задачу;
  задачі стають у чергу; воркер меле по одній. Ніхто нікого не блокує.
* **Фонова робота без дедлайну.** Переіндексація великого банку може тривати
  хвилини — це нікого не вішає, бо це фон, а не хук у сесії.
* **Порядок файлів — довільний.** Усередині одного завдання файли індексуються в
  будь-якому порядку — на якість пошуку це не впливає, бо все одно все лягає у
  вектори, які не мають пріоритетності. Пріоритети — лише між *задачами* (нижче),
  не між файлами.
* **Статус назовні.** Watcher публікує стан (що в черзі, що індексується,
  прогрес, останні помилки) — це живить UI й ендпоінт здоровʼя.

**Пріоритетна черга (щоб великий реіндекс не глушив усе).** Робота ставиться в
чергу **почанково**, з пріоритетами, а не одним монолітним завданням:

* **Високий пріоритет — поодинокі/інкрементальні зміни.** Правка одного файлу
  влітає в **початок** черги й переіндексовується майже одразу.
* **Низький пріоритет — масовий реіндекс** (новий банк з нуля, ціла тека, «повний
  реіндекс банку»). Він ріжеться на чанки й меле у фоні **між** високопріоритетними
  задачами, тому додавання банку на годину роботи **не глушить** решту: дрібні
  правки в інших банках усе одно проскакують уперед і швидко індексуються.
* **Чанкова гранульованість** — велике завдання можна витіснити після будь-якого
  чанка; нове термінове не чекає, поки догойдається ціла година.

Це поведінка за замовчуванням (**прапорець, типово ввімкнений**); за потреби
пріоритезацію можна вимкнути — тоді все меле простим FIFO без випередження.

**Що з хуками.** Хуки Claude Code більше **не потрібні для переіндексації** — це
робить watcher сам. Але й авто-інжектом вони більше **не вмикаються самі**:
`mnemo init` не пише **жодного** хука. Механізм лишається як **насіння** — код
цілий, вмикається явним прапорцем, — бо основний доступ до памʼяті це **MCP**
(агент шукає, коли сам захоче), а дисципліну «шукай перед роботою» тримає
**правило** (`.claude/rules/mnemo-memory.md`), не хук.

Причина, чому саме правило, а не авто-інжект: хук вкидає секції **до** того, як
задача сформульована, і агент, побачивши памʼять у контексті, вважає, що вже
шукав. Це гірше за відсутність інжекту — фальшиве покриття. Правило, яке
вимагає **явного** виклику `search`, дає перевірний факт: або кликав, або
ні.

**Два насіння, обидва off:**

* **`memory-hook` (SessionStart)** — підкидає **`MEMORY.md` банку плюс карту
  структури** (де логи, де топіки, де памʼять агентів). Це **карта, а не
  відповіді**: індекс прямо каже «деталі шукай через `search`», тому
  фальшивого покриття не створює. Читає файл **з диска**, тому не залежить від
  того, чи бекенд живий, і не може підвісити старт сесії. Замінює нативне
  автозавантаження `MEMORY.md`, якого банк у репозиторії не отримує.
* **`hook-inject` (UserPromptSubmit)** — той самий, що й був: ембедить промпт і
  підкидає top-N секцій. Швидкий пошук, не важкий ingest, але вмикати його —
  свідоме рішення з описаною вище ціною.

## 6. Ядро та фасади доступу

**Основний принцип** — одне **ядро-бекенд** тримає всю логіку (реєстр банків +
індекс + watcher + провайдер) і віддає її через **один внутрішній API** (loopback).
Обличчя — **тонкі клієнти** цього API, а не окремі рушії (запис і читання — одна
когерентна система, як у v2).

**Два довгоживучі процеси** (розділяємо навмисно):

* **Ядро-бекенд** — завжди підняте: приймає запити пошуку/індексації, стежить за
  файлами (watcher), веде чергу й логи, звертається до моделі за векторами. Саме на
  його постійній роботі тримається автономність.
* **Модель-демон** (embed-резидент, розділ 4) — окремо тримає векторну модель
  **гарячою**: стежить, щоб вона відповідала, сам піднімається на першу потребу
  й перезапускається при потребі; idle-виходу немає (розділ 4). Уся логіка
  життєвого циклу моделі — тут, не в ядрі.

Обличчя над ядром (усі — клієнти одного API):

* **MCP — два обличчя, і різниця між ними принципова.**
  * **`/mcp` — проєктне, тільки читання: `search` (+**опційний**
    `path_prefix` — звузити до теки/файлу) і `tree`.** **Адресується
    токеном банку**: підключення вказує, з яким банком працює, і вказує це
    саме креденшлом — у шляху банку немає (рішення #24). Тож проєкт чи
    окремий агент має **своє MCP на свій банк** (саме так розводиться доступ,
    коли потрібна ізоляція). Аргументом тула банк передати не можна, і
    сервісний токен це обличчя **не відкриває** — йому нема до якого банку
    резолвитись. `write` **не робимо** (рішення #6): редагування — лише
    нативними файловими інструментами.
  * **`/mcp-admin` — керування сервісом: `banks`, `bank_add`, `bank_remove`,
    `reindex`, `status`, `logs`.** Банк тут — аргумент, **тільки сервісний
    токен**. Сюди пішов і `reindex`: watcher переіндексовує сам за секунди
    після збереження, тож на проєктному обличчі це був слот тула, витрачений
    у кожній сесії на кнопку, яку майже нікому не треба (рішення #21).

  **Чим це реалізовано, щоб не було плутанини:** MCP — це **FastMCP** (клас із
  офіційного `mcp` SDK), а FastAPI його лише **хостить**, змонтувавши як
  ASGI-піддодаток на `/mcp`. Два фреймворки не змішані — вони вкладені один в
  один, і FastAPI у протокол MCP не заглядає. Один процес, один порт, і тули
  кличуть внутрішні функції бекенда **напряму** — саме тому окремий процес під
  MCP відкинуто: він мусив би ходити до бекенда по HTTP, а це другий сокет,
  подвійний запис у журнал на кожен виклик і ризик заклинити, чекаючи на
  воркер, у черзі якого сам і стоїть.
* **CLI** — той самий `search` / `ingest` / `reindex`, але тепер **клієнт
  сервісу**: команда = виклик того самого API, а не окремий процес, що сам відкриває
  індекс (інакше було б два писаки в одну базу). Ops-команди (`warmup`, `init`)
  лишаються локальними.
* **Web UI** — браузерний клієнт того самого API (розділ 7).
* **Дзеркало тулів — `/mcp-tools/<tool_name>`** — ті самі три функції звичайним
  HTTP: відправив запит, отримав відповідь, **без JSON-RPC і без стріму**. Це
  поверхня **для людини й для скрипта перевірки живості**: її видно у Swagger,
  її можна тикнути curl-ом. Імена ендпоінтів і параметри — **1:1** як у
  MCP-тулів, віддає **той самий текст**, що бачить агент (JSON — опційно), тому
  дзеркало не може розійтися з оригіналом: розбіжність була б видна відразу.
* **(Опційно) Хуки-насіння** — не вмикаються самі (розділ 5).
* **HTTP / loopback** — тут дві різні поверхні, і різниця принципова:
  * `/api/*` — **приватний** канал кабінет↔бекенд. Не документований, зі
    OpenAPI-схеми прихований, обіцянок сумісності не дає. Саме тут живуть речі,
    яких зовні бути не має: `fs/dirs` (лістить теки на диску), видалення банку,
    сирий вміст файлу.
  * `/mcp` і `/mcp-tools/*` — **зовнішні**: перше для агентів
    (офіційний MCP по JSON-RPC), друге для людини.

  Ендпоінт запису `.md` у v1 не потрібен (писати нема кому: `write`
  скасовано, UI-редагування — поза v1), тож додамо його лише разом із
  UI-редагуванням.

Пошуковий пайплайн під усіма обличчями — з v2: vector kNN + FTS5 + RRF + гейт
проти порожніх/слабких збігів. Область пошуку — банк цілком (він плаский).

**Пошук під час індексації — статус, а не блокування.** Пошук **ніколи не чекає**
й **ніколи не висить**: завжди відповідає з поточного індексу + **статус стану**:

* **`indexing`** — зараз щось індексується (за потреби — приблизна кількість у
  черзі). Віддаємо, що вже є (частина або поки нічого); свіжі зміни ще можуть бути
  не в базі.
* **`empty`** — у банку **взагалі нічого не проіндексовано**. Окремий, явний сигнал
  «тут порожньо» — не плутати з «пошук нічого не знайшов»: `empty` = «бази ще
  немає», а порожня видача при `ready` = «база є, але релевантного збігу немає».
* **`ready`** — черга порожня, індекс актуальний: звичайна відповідь.

На першому білді `empty` та `indexing` збігаються (порожньо + йде індексація). Так
агент завжди отримує миттєву відповідь і чесно розрізняє три речі: «порожньо», «ще
індексується», «готово». Принцип мʼякої деградації з v2, але з явним станом.

**Логи запитів та індексації (спостережуваність, у v1).** Сервіс веде журнал усіх
подій, щоб їх можна було прослідкувати в кабінеті — навіть у першій версії. Дві
категорії подій:

* **Запити (головне).** Кожен пошук пишеться як пара «вхід → вихід»: текст запиту,
  банк, час, статус (`indexing` / `empty` / `ready`) — і **які
  саме чанки повернулися** у відповідь (файл + секція + бал). Так завжди видно, що
  прийшло на запит і що пішло у відповідь.
* **Індексація.** Кожна подія переіндексації: «файл X змінено → запущено
  індексацію цього файлу» або «запущено повний реіндекс банку/теки». Тип події
  (поодинокий файл / масовий реіндекс) — окрема категорія, щоб події можна було
  розрізняти й фільтрувати.

Журнал — частина **записуваного стану** сервісу (той самий реалм, що й індекси; не
в git, ротований). Кабінет дає його **фільтрувати**: за конкретним банком (усі
його зміни/запити) і **загально по всіх банках** одразу.

## 7. Web UI (простий кабінет)

**Основний принцип** — легкий локальний кабінет, щоб **бачити й контролювати**
памʼять очима, а не наосліп. Свідомо простий.

**Обсяг v1 (мінімум) — зафіксовано (рішення #7):**

* **Список банків** — які підключені, корінь, git чи ні, стан індексу (скільки
  файлів/чанків, коли востаннє індексовано, скільки у черзі, помилки).
* **Дерево файлів банку** — навігація вкладеністю (видно, багато файлів чи ні);
  клік → **перегляд вмісту** `.md` (просто текст).
* **Контроль індексу** — кнопка «повний реіндекс банку» та «переіндексувати
  конкретний файл». Видно чергу й прогрес.
* **Візуалізація чанків (проста)** — той самий перегляд файлу, але з
  **лініями-роздільниками**, що показують межі чанків: одразу видно, як файл
  порізало на одиниці памʼяті. Без окремого складного вʼю — просто «полосочки»
  поверх тексту.
* **Журнал подій** — стрічка логів запитів та індексації (розділ 6): що спитали /
  що повернулось, який файл переіндексовано; фільтр за банком і загальний вигляд
  по всіх банках.

**Не в v1 (пізніше):**

* **Редагування `.md` з кабінету** — лишаємо **нативним файловим інструментам**
  (узгоджено з рішенням #6). Якщо колись додамо — запис іде у файл, а watcher
  переіндексовує; UI однак ніколи не чіпає індекс напряму.
* Попередній перегляд результатів пошуку, підсвітка, розширена статистика.

UI — це **тонкий клієнт HTTP-API**. Жодної власної логіки памʼяті в ньому немає.

## 8. Джерело правди (рішення зафіксовано)

`.md` — завжди джерело правди. Питання «де саме вони лежать» **знято**: файли
лежать **на місці**, там, куди вказує корінь банку, і сервіс індексує їх **у цьому
місці**. Ніякого окремого «центрального сховища, яким володіє сервіс», як
конкурентної моделі немає. Різниця лише в тому, **чи це місце версіонується git**:

* корінь усередині git-проєкту → памʼять їде з `git clone`, ревʼюється в PR;
* корінь — окремі файли на диску → просто локальні файли, поза git.

Обидва випадки — **один і той самий механізм**: зареєстрований корінь + індексація
на місці. Раніше розглянутий вибір «git-native vs сервіс-володіє vs гібрид»
**згорнуто** на користь цієї єдиної моделі: **файли на місці, git-трекінг —
властивість місця, а не окремий режим.** Сервіс тримає лише **реєстр коренів** і
**похідні індекси** (у своєму стані), але самими `.md` не «володіє» — вони там,
де їх поклав користувач чи проєкт.

## 9. Розгортання: нативно зараз, Docker — пізніша опція

**Рішення (зафіксовано): перша версія — нативна, без Docker.** Це просто
Python-код, що працює в системі (Python є всюди на таких машинах). Причини саме
такого вибору:

* **Банки розкидані по всій ФС.** Корені — у різних місцях системи; нативний
  процес має **прямий доступ** до всіх них одразу. У Docker довелося б монтувати
  купу розкиданих тек у контейнер — незручно й крихко саме під цей сценарій.
* **Стеження працює надійно.** Файли й watcher — на одній ФС, події ФС приходять
  чесно (жодного host↔container inotify-розриву).
* **Нуль зовнішніх залежностей.** Ні Docker Desktop, ні WSL2. На Windows це
  критично: Docker Desktop тягне WSL2, який ми свідомо прибрали з нативного
  інсталу.

**Docker лишається опцією — але пізнішою й не привʼязаною до WSL2.** Коли
зʼявиться потреба (роздати команді єдине середовище, крутити на Linux-сервері) —
його можна додати, бо сервіс **deployment-agnostic**: той самий код працює
нативно або в контейнері. Природний дім Docker — **Linux/сервер**, де немає ні
WSL2, ні проблеми зі стеженням за хостовою ФС. На Windows Docker **не є** шляхом
за замовчуванням і в першу версію **не входить**. Готовий контейнерний профіль
для резидента вже описаний у `docs/containers/README.md` — його беремо як
довідку на потім, а не як залежність зараз.

Підсумок: **зараз — один нативний сервіс на Python; Docker — коли й де він реально
доречний (Linux/сервер/команда), як додаткове пакування, а не основа.**

## 11. Майбутнє / опційні шари (не для першої версії)

* **Віддалені джерела банку (Notion / Google Drive / інші)** — як **адаптер
  джерела**: корінь банку синкається з Notion чи Drive, а далі той самий пайплайн
  `файли → чанки → вектори`. **Двонаправлений** sync (правити в Notion → міняється
  файл → реембединг, і навпаки) — це **важка** задача (розвʼязання конфліктів);
  беремо як майбутнє, спершу однонаправлено (джерело → `.md`).
* **Граф знань** — сутності/звʼязки поверх дерева файлів. Опційний шар, коли
  простого дерева стане замало. Не вводимо, поки немає доведеної потреби.
* **Візуалізації** — карта чанків, теплокарта релевантності, звʼязки між файлами.
* **Кілька embeddings-провайдерів під різні банки** — приватне тільки `local`,
  масове/публічне — швидший `api`.

## 12. Антипатерни, яких і далі свідомо уникаємо

* **Індекс як джерело правди / пряме редагування індексу.** Ніколи. Пишемо у
  `.md`, індекс — завжди похідний (незмінно з v2).
* **Немає prune → стейл при ренеймі/видаленні.** Prune обовʼязковий (з v2).
* **Важкий граф знань там, де досить дерева файлів.** Не ускладнюємо наперед.
* **Docker як основа/примус.** У v1 Docker немає взагалі; далі — лише опція, не
  привʼязана до WSL2, дім — Linux/сервер. Не тягнемо WSL туди, де не треба.
* **Модель тягнеться неявно.** Тільки явний `warmup`; хук/сервіс не качає 2.2 ГБ
  сам (з v2).
* **Двонаправлений sync без явного розвʼязання конфліктів.** Спершу однонаправлено.
* **Хмара/дані назовні за замовчуванням.** Сервіс — loopback-локальний; будь-який
  вихід назовні (api-провайдер, Notion) — свідомий opt-in.
* **Дві кодові бази під native і Docker.** Один deployment-agnostic сервіс.

## 13. Стан рішень

**Зафіксовано:**

1. **Джерело правди** — файли **на місці**; git-трекінг — властивість місця, не
   окремий режим (розділ 8).
2. **Розгортання** — **нативно, без Docker** у першій версії; Docker — пізніша
   опція, не привʼязана до WSL2, дім — Linux/сервер (розділ 9).
3. **Стеження** — нативний watcher на подіях ФС (файли й демон на одній ФС).
4. **Дві служби** — ядро-бекенд (watcher + API + індекс, завжди підняте) і окремий
   модель-демон (embed-резидент: підіймається на першу потребу, далі тримає
   модель гарячою без idle-виходу, перезапуск); обидва нативні, без Docker
   (розділи 4, 6).
5. **Банк** — довільна коренева тека будь-де; багато банків, корені розкидані по
   системі; реєстр коренів у сервісі (розділ 2).
6. **`write` — не робимо.** Редагування памʼяті — лише нативними файловими
   інструментами; сервіс не пише `.md` за агента (розділ 6).
7. **Web UI v1** — список банків + дерево + перегляд тексту + реіндекс (повний / по
   файлу) + **проста візуалізація чанків лініями-роздільниками**; **без
   редагування** (розділ 7).
8. **Віддалені джерела (Notion / Google Drive)** — пізній опційний адаптер,
   **зараз не розробляється взагалі** (розділ 11).
9. **Доля v2** — v3 **повністю замінює** v2 як цільову архітектуру; **без**
   паралельних гілок.
10. **Пріоритетна черга** — почанкова; поодинокі/інкрементальні зміни — високий
    пріоритет (у початок), масовий реіндекс — низький, у фоні (прапорець, типово
    ввімкнений). Порядок *файлів* довільний; пріоритети лише між задачами (розділ 5).
11. **Пошук під час індексації** — не блокує; віддає поточний індекс + статус
    стану (`indexing` / `empty` / `ready`); `empty` (бази немає) ≠ порожня видача
    (немає збігу) (розділ 6).
12. **Логи запитів та індексації — у v1.** Журнал: запит → повернуті чанки, і
    події індексації (файл / повний реіндекс); фільтр за банком і глобально
    (розділи 6, 7).
13. **Банк плаский — без внутрішніх скоупів.** Немає поділу `project` / `agent`:
    вибрана тека цілком = один великий індекс. Ізоляція досягається **окремими
    банками** (напр. банк на агента) + окремими MCP-підключеннями (розділи 2, 6).
14. **Транзиція — на місці, v2 не лишається.** Наявний `src/` еволюціонує у v3;
    паралельних гілок v2/v3 немає — v3 стає єдиною версією. Індекс ключується
    **коренем банку**, тому індекси, зроблені під корінь *проєкту*, здебільшого
    осиротіють: v3 їх не відкриває і **не видаляє автоматично** (на машині може
    лишатись проєкт зі встановленим рушієм v2 — тихе видалення зламало б йому
    пошук). Прибирання — явне, через `mnemo doctor`.
15. **Хуки — насіння, яке не вмикається саме.** Реіндекс робить watcher, а
    авто-інжект `mnemo init` **більше не додає**: жодного хука в
    git-трековане wiring автоматично не потрапляє. Механізм лишається цілим і
    вмикається явним прапорцем — два насіння: `memory-hook` (SessionStart,
    підкидає `MEMORY.md` + карту структури) і `hook-inject` (UserPromptSubmit,
    top-N секцій). Дисципліну «шукай перед роботою» тримає **правило**, не хук
    (розділ 5).
    > *Попередня редакція* дозволяла авто-інжект як «опційний приклад, який
    > даємо готовим». Скасовано: хук вкидає секції до того, як задача
    > сформульована, і агент вважає, що вже шукав. Фальшиве покриття гірше за
    > його відсутність.
16. **Дві поверхні HTTP, а не одна.** `/api/*` — **приватний** канал
    кабінет↔бекенд: не документований, прихований з OpenAPI, без обіцянок
    сумісності (там `fs/dirs`, видалення банку, сирий файл). Назовні —
    `/mcp` (офіційний MCP по JSON-RPC, для агентів) і
    **`/mcp-tools/<tool_name>`** (ті самі три функції звичайним HTTP, для людини
    й для перевірки живості). Дзеркало віддає **той самий текст**, що бачить
    агент, а імена й параметри бере 1:1 з MCP-тулів — розбіжність була б видна
    відразу. Другого «публічного REST» зі своїм словником **не робимо**
    (розділ 6).
17. **MCP — FastMCP, змонтований у той самий процес.** Один порт, тули кличуть
    внутрішні функції бекенда напряму. Окремий процес/порт під MCP відкинуто
    (розділ 6).
18. **Уся памʼять банку вкладається в один корінь.** Не `.claude/memory/` **і**
    `.claude/agent-memory/` на одному рівні, а `.claude/memory/` з `logs/`,
    `topics/`, `agents/<role>/` всередині. Тоді корінь банку = `.claude/memory`,
    а `agents/`, `rules/`, `skills/`, `settings.json` лежать **поза** банком і в
    памʼять не потрапляють — **за побудовою, без ексклюдів**. Ексклюди свідомо
    не заводимо: межа теки — правило позитивне й самопідтримне, а список
    винятків гниє (нова тека зʼявилась, дописати забули — вона тихо в індексі).
19. **Правило памʼяті портативне.** `.claude/rules/mnemo-memory.md` = переносне
    ядро (структура, тригери пошуку, дисципліна запису, імена MCP-тулів) +
    тонка обгортка про Claude Code. Ядро мусить працювати вставленим у system
    prompt будь-якого агента: MCP уже стандартний, тож нова платформа — це
    «підключи MCP + вкинь ядро».
20. **Банк задає підключення, а не аргумент тула.** У `search` і `tree` на
    `/mcp` параметра `bank` **немає**. Було виміряно на живому
    сервісі: підключення до `/mcp/mnemo` з `search(bank="odin-crm")` віддавало
    памʼять іншого банку — тобто «підключення вказує, з яким банком працює»
    (розділ 6) не виконувалось. Аргумент лишається на поверхнях під
    **сервісним** токеном (`/mcp-tools/*`, адмінські тули), де назвати банк —
    і є сенсом поверхні.
21. **Два обличчя MCP: проєктне (читання) й адмінське (керування).**
    `/mcp` — `search` + `tree`, і більше нічого. `/mcp-admin` — без
    сегмента банку, шість тулів керування (`banks`, `bank_add`,
    `bank_remove`, `reindex`, `status`, `logs`), **тільки сервісний токен**.
    Два окремі екземпляри FastMCP, а не один із фільтром: список тулів
    клієнт кешує на хендшейку, тож «оголосили, але потім відмовили» показало
    б агентові шість тулів, які він ніколи не викличе.
22. **У кожного банку свій токен.** Карбується при реєстрації, живе в
    `banks.json` поруч із банком, відкриває MCP-обличчя саме цього банку;
    токен банку A на URL банку B — `401`. Саме він, а не сервісний,
    потрапляє у wiring проєкту. **Це найменша достатня привілея, а не
    стіна**, і так і записано: власник сервісного токена відкриє будь-який
    банк, і хто прочитає `banks.json` — прочитає всі токени. Купується цим
    одне, і воно того варте: віддати колезі `.mcp.env` одного проєкту більше
    не означає віддати кожен інший банк на машині.
23. **`mnemo init` знає про конвенцію шаблонів.** Якщо в проєкті є
    `.mcp.json.template`, запис іде **в шаблон** (плейсхолдерами), значення —
    у git-ігнорований `.mcp.env`, підстановки — у `mcp-setup.sh`. Причина не
    естетична: `mcp-setup.sh` перезаписує `.mcp.json` цілком, тож запис прямо
    туди зникає при наступному запуску **без помилки й без сліду**. Без
    шаблону — прямо в `.mcp.json` з літеральним токеном, і `.gitignore`
    отримує рівно один рядок. **У git-трекований файл літеральний токен не
    пишеться ніколи: `init` відмовляється** (друкує `git rm --cached`, не
    пише нічого, виходить з ненульовим кодом) — відмову відкочують однією
    командою, а токен у трекованому файлі не відкотити ніяк. Трекнутість
    визначається **читанням `.git/index`**; `init` git не запускає ніколи —
    ані щоб перевірити, ані щоб виправити.

24. **Токен визначає банк — у шляху банку немає.** Адреса проєктного обличчя
    це `http://127.0.0.1:8918/mcp?token=<bank-token>`, і більше нічого: раз
    токен належить банку, назвати банк ще раз в URL — це другий голос, вільний
    суперечити першому. Разом із сегментом пішли заголовок `X-Mnemo-Bank`,
    правило «якщо банк один — беремо його», змінна `MNEMO_BANK` і
    percent-encoding назви з пробілами й кирилицею. Сервісний токен це обличчя
    **не відкриває**: йому нема до якого банку резолвитись, а вгадувати — і є
    той баг, від якого все це рятує. Ціна — URL більше не каже, для якого
    банку запис; це значення несе **імʼя MCP-запису** (`mnemo`,
    `mnemo-notes`), яке людина в конфізі й читає. Косметичного сегмента, що
    його маршрутизація ігнорує, свідомо не додаємо: компонент шляху, який
    означає не те, що написано, гірший за відсутній.

25. **Осиротілі індекси прибирають явно, і ніколи не автоматично.** Індекс
    зветься `sha1(канонічний корінь)[:16].db` — банк знаходить свій файл
    **обчисленням**, і зворотного звʼязку немає: у теці `state/` лежать самі
    файли, ніщо в них не каже, що вони чиїсь. Тому зняття банку без
    `drop_index`, правка `root` руками (id перераховується з нового кореня —
    навмисно, інакше банк тихо віддавав би чанки старої теки) і перехід з v2,
    де ключем був корінь **проєкту**, а не банку, лишають файли, яких уже
    ніхто не відкриє. Вони інертні: не в пошуку, не в `/api/banks`, не в
    журналі — коштують лише диск.
    `doctor` їх **показує** (`orphan indexes N (розмір)`), `mnemo
    clean-orphans` — і тільки вона — **видаляє**, друкуючи перед тим повний
    список і чекаючи підтвердження (`--dry-run` дивиться, `--yes` для
    скриптів). Розділення не косметичне: діагностика, яка дорогою щось стирає,
    це діагностика, яку перестають запускати «просто подивитись». Прибирання
    на старті сервісу відкинуто з тієї ж причини — тимчасово знята з реєстру
    тека означала б негайну втрату індексу й повну перебудову замість
    `git checkout`.
    Дві властивості тримають це безпечним і **перевіряються тестами**:
    нечитаний `banks.json` дає **відмову**, а не «банків немає» (інакше
    список орфанів = всі живі індекси), і `delete_index` перечитує реєстр
    **у момент видалення**, тож банк, зареєстрований між показом списку й
    підтвердженням, застарілим списком не зітреш. `service.db` виключено
    **за іменем**: виводити «це не банк» з його вмісту — один умовивід від
    того, щоб видалити власний журнал сервісу.

**Відкритих архітектурних розвилок більше немає — ядро зафіксоване.**
