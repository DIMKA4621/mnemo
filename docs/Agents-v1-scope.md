## 1. Персона — ядро без змін проти старого концепту

Тека агента (`CLAUDE.md` + руси + скіли + MCP + власний банк памʼяті) — `Agents-design.md` §1, не переглядається.

**Нове:** джерело теки при створенні — не лише «створити з нуля під `~/.mnemo/agents/<slug>/`», а й **вказати будь-яку наявну робочу теку** (проєкт).
Якщо в ній уже є `CLAUDE.md`/`.mcp.json`/`.claude/` — перед створенням показується **діалог підтвердження**: коротке превʼю знайденого (CLAUDE.md, MCP-сервери, скіли) і кнопка «створити» — не мовчазна адопція.
Підтверджене адоптується as-is, нічого не перезаписуючи; чого нема — добудовується (той самий підхід, що вже є в `scaffold.py::init_project` — адитивно, ідемпотентно, ніколи не б'є по наявному).

## 2. Запуск — mnemo-native або «головний агент проєкту»

Персона запускається або сама по собі (mnemo як власна тека), або **як головний агент конкретного проєкту** — тобто той самий персона-процес, який Claude Code підняв би, зайшовши в теку проєкту напряму.
Спільна інфраструктура запуску Claude Code, не окрема mnemo-специфічна.

## 3. Сесія — повний паритет з CC harness, не урізаний чат

Обовʼязково в v1, не «пізніше доробимо»:

- стандартні тули, MCP, скіли, руси, памʼять, `CLAUDE.md`, слеш-команди — усе, що має звичайна сесія Claude Code;
- **надсилання й відображення файлів у сесії** (вкладення, картинки) — раніше в `Agents-design.md` §6 це було позначено як «деталь фази 5»; тепер це **мінімум**, не відкладене.

**Уточнення (MN-44, звужено лідом 2026-08-29):** «відображення» вище означає лише вихідне вкладення людини — chip/thumbnail у браузерному DOM, поза терміналом; «надсилання» покрито повністю (upload-ендпоінт → шлях файла вставляється в термінал буквеним текстом, як звичайний drag-and-drop у реальний термінал).
Вхідні зображення з виводу самого агента спеціально не рендеряться: CLI живе в сирому PTY (§3 вище, `Agents-design.md` §6) і не емітує inline-image термінальний протокол (iTerm2/Kitty/Sixel чи подібний), а якби й емітував — це поза контролем mnemo.

Рантайм — `Agents-design.md` §6 без змін: сесія живе на бекенді (Claude Agent SDK, процес сервісу), WS-стрім, перемикання клієнта не спиняє генерацію.

## 4. Аутентифікація — per-agent вибір методу

Уточнення до `Agents-design.md` §3: вісь вибору — **метод автентифікації**, не просто «стандартний/кастомний хост»:

- **системна** — авторизація самого Claude Code (як є, підписка/ключ);
- **проксі** — свій хост/порт + список модель-замінників.

`launch.json` лишається місцем зберігання (per-agent, у теці агента), форма поля саме під це уточнюється.

## 5. Мультиагентність — нове, не було в старому концепті

Найбільше доповнення проти 2026-08-20.
Персона повинна вміти:

- **звертатись до інших своїх сесій/персон**: надіслати повідомлення, прочитати останні N, отримати самарі сесії, перервати виконання — та сама форма, що вже є в цьому харнессі (`SendMessage`/`ListAgents`/`TaskStop`), винесена як інструмент усередині агентських сесій mnemo;
- **спавнити сабагентів і бачити їх** — бажано візуально в самому кабінеті mnemo (дерево/лог активних сабагент-ранів), не лише в терміналі;
- **якщо в теці вже описані сабагенти** (`.claude/agents/*.md`) — пропонувати запустити кожного одразу як окрему топ-рівневу персону/сесію, не вкладено.
  Природне продовження вкладки «Реєстр» (`Agents-design.md` §4): той самий скан-і-запропонуй патерн, застосований до готових агентів, а не лише MCP/скілів/рулів.

Це найбільший шматок нового scope — імовірно, заслуговує окремого розділу архітектури (менеджер сесій, а не лише `agent_runtime.py` з §6), коли дійдемо до фазування.
