# mnemo v3 — вимоги (functional + non-functional)

> **Третій документ трійки:**
> - `Memory-design-v3.md` — *що і чому* (архітектура, джерело правди рішень);
> - `Memory-requirements-v3.md` — *що система мусить робити* (FR) і *як мусить
>   поводитись* (NFR) — цей файл;
> - `Memory-implementation-v3.md` — *як і в якому порядку* (стек, блоки, фази).
>
> Вимоги — це критерії приймання: реалізацію звіряємо з цим списком.

---

## FR — функціональні вимоги (що система робить)

- **FR-1 · Банки.** Реєструвати довільні кореневі теки будь-де на диску; багато
  незалежних банків; реєстр — людиночитний JSON; кожен банк має власний індекс.
  Банк **плаский** — жодних внутрішніх скоупів; уся тека = один індекс. Потрібне
  розділення (напр. на агента) → **окремий банк** + окреме MCP-підключення.
- **FR-1a · Уся памʼять банку — під одним коренем.** Канонічна розкладка:
  `.claude/memory/` з `MEMORY.md`, `logs/`, `topics/`, `agents/<role>/` всередині —
  а не `memory/` та `agent-memory/` двома теками на одному рівні. Корінь банку —
  `.claude/memory`, тому `agents/`, `rules/`, `skills/`, `settings.json` лежать
  **поза** банком і в памʼять не потрапляють **за побудовою**. Механізму ексклюдів
  (`exclude` у реєстрі, `.mnemoignore`) v3 **не має** — межа теки замінює його, і це
  свідомий вибір: позитивне правило само себе тримає, список винятків гниє.
- **FR-2 · Індексація.** `.md → чанки(за заголовками) → вектори → sqlite-vec + FTS`;
  hash-diff (лише змінене), prune (видалене зникає), per-batch commit, батч ~16 чанків.
- **FR-3 · Пошук.** vector + FTS + RRF у межах банку; повертає релевантні секції;
  **ніколи не блокує**; до відповіді додає статус `indexing` / `empty` / `ready`
  (`empty` = бази немає ≠ «нема збігів»). **Опційно** — звуження `path_prefix`
  (тека, рідше файл) у межах банку; не обовʼязкове, зручність навігації.
- **FR-4 · Автостеження + черга.** Watcher сам помічає зміни банків і ставить у чергу;
  пріоритет: поодинокі правки > масовий реіндекс (прапорець, типово ввімк.); робота — у фоні.
- **FR-5 · Обличчя.** MCP (search / tree / reindex) — **основний** доступ, по HTTP
  (FastMCP, змонтований у бекенд), **адресоване по банку** (проєкт/агент може мати
  своє MCP на свій банк); **дзеркало `/mcp-tools/<tool_name>`** — ті самі три функції
  звичайним HTTP без JSON-RPC і без стріму, імена й параметри 1:1 з тулами, віддає той
  самий текст (JSON опційно), видне у Swagger — для ручної перевірки й перевірки
  живості; CLI — клієнт сервісу; Web UI. `/api/*` — **приватний** канал кабінет↔бекенд,
  зі схеми прихований. `write` **не робимо** — правки лише нативними файловими
  інструментами.
- **FR-5a · Хуків немає.** `mnemo init` не додає **жодного** хука, і прапорця,
  який би його додав, теж немає — обидва насіння (`memory-hook`, `hook-inject`)
  прибрані разом із командами. `--migrate` знімає ті, що лишилися в проєктах від
  попередніх поколінь. Дисципліну «шукай перед роботою» тримає **правило**, і
  тільки воно: два механізми, що кажуть одне й те саме, можуть розійтися.
- **FR-6 · Логи.** Події `query` (запит → повернуті чанки) і `index` (файл/масовий реіндекс)
  у SQLite `service.db`; читання з фільтром за банком і часом.
- **FR-7 · Web UI (v1).** Список банків, дерево файлів, перегляд `.md`, **chunk-viz
  лініями-роздільниками**, кнопки реіндексу (повний / по файлу), журнал; **без редагування** у v1.
  Плюс **реєстрація нового банку з кабінету**: вибір теки браузером тек, який обходить ФС на
  боці бекенда (`GET /api/fs/dirs`), бо сторінці шлях до вибраної теки не віддається —
  ані через `webkitdirectory`, ані через `showDirectoryPicker()`. Реєстрація одразу ставить
  `bulk` у чергу, тож окремої команди не потрібно. «Без редагування» стосується `.md`:
  реєстр — не памʼять.
- **FR-8 · Провайдери ембедингу.** `local` (e5-large, за замовчуванням); опційний `api`;
  per-service або per-bank; зміна провайдера → повна перебудова індексу банку.
- **FR-9 · Керування сервісом.** Команди `mnemo service start | stop | status | restart` —
  іменовані процеси, видимий стан (PID / порт / банки / черга).
- **FR-10 · Самооновлення рушія.** Бекенд перевіряє GitHub-теги/релізи (не кожен коміт
  `master`) фоново за таймером і вручну; застосування — лише по явному кліку в кабінеті,
  з попередженням про зупинку сервера. Нова версія стейджиться (завантаження + окремий
  venv під `versions/<tag>/`), поки стара й далі відповідає; перемикання — health-gated:
  якщо новий білд не піднявся, автоматичний відкат на попередню версію, а не мовчазна
  відмова чи мертвий сервіс. Оновлюється лише сам рушій — проєкти, підключені через
  `init`, залишаються клієнтами й цим процесом не займаються (design #33).

  *Додано зараз, а не мовчки:* решта FR звіряють фази 0–7 з `Memory-implementation-v3.md`,
  а самооновлення — рішення поза цими фазами, ухвалене й повністю реалізоване окремо
  (усі 13 кроків закриті й перевірені живцем). Без власного FR ця вимога лишалася б
  задокументованою лише в design §13 #33 і contracts §9.9 — при тому, що вона рівно
  така сама «критерій приймання», як решта списку, і design-документ прямо каже, що
  implementation-план у ньому свідомо не тримають.

## NFR — нефункціональні вимоги (як система поводиться)

- **NFR-1 · Тихі процеси, без вікон.** Жодного блимання консолі. Демони й будь-які
  спавни — windowless: Windows `CREATE_NO_WINDOW` / `pythonw`; Linux — відчеплені
  (`start_new_session`, stdio→devnull) / systemd.
- **NFR-2 · Нуль спавнів.** MCP — по **HTTP** (Claude Code конектиться до URL,
  процес не запускається), а хуків немає взагалі (FR-5a). Тобто спавнів не
  «типово нуль», а нуль: у сесії не запускається жодного процесу mnemo.
- **NFR-3 · Always-on + керованість.** Сервіс автозапускається і працює у фоні навіть без
  активної сесії; іменований; повний контроль `start/stop/status/restart`. On-demand — fallback.
- **NFR-4 · Неблокування.** Жодне обличчя чи хук не вішає сесію; пошук — миттєвий;
  індексація — завжди у фоні, без дедлайну.
- **NFR-5 · Продуктивність ембедингу.** Throughput обмежений CPU (стеля). Потоки демону
  `cpu*3//4` (override `MNEMO_EMBED_THREADS`). **Конкурентність** (терміновий пошук не
  чекає на bulk-білд) дають **дві смуги в одному резиденті**, а не пул процесів:
  15.7 с → ~0.37 с, батч платить ~2 %, RAM +0. Пул `N` розглянуто й **не реалізовано**
  (`Memory-implementation-v3.md` §4). Реальні цифри — заміряти, не обіцяти.
- **NFR-6 · Встановлення й автозапуск per-OS.**
  - *Linux:* `systemd --user` unit (`systemctl --user start/stop/status`), `loginctl
    enable-linger` для always-on; alias/PATH для CLI.
  - *Windows:* реєстрація `mnemo` у **PowerShell-профілі**; **Task Scheduler** (прихований)
    для автозапуску при вході; windowless-лаунчер демонів/хуків.
  - Без WSL, без Docker, без PowerShell 7, без зміни системного PATH.
- **NFR-7 · Безпека.** Усе на loopback за замовчуванням; API під токеном (як `embed.token`);
  Web UI лише локально. Вихід назовні (`api`-провайдер) — свідомий opt-in.
- **NFR-8 · Retention логів.** Логи обмежені за часом: env `MNEMO_LOG_RETENTION_DAYS`
  (типово 30 ≈ місяць); авто-prune старіших на старті + періодично; опційний backstop за рядками.
- **NFR-9 · Ресурси.** Одна копія локальної моделі в RAM на машину:
  * **усталений стан — ~1.6 ГБ.** Це надійна цифра: 1503–1526 МБ на всіх пробуваних
    навантаженнях, розкид 22 МБ.
  * **транзієнтний пік — не ~1.6 ГБ.** Він залежить від розміру батчу й **найдовшої
    послідовності в батчі**: ~1.56 ГБ на коротких англійських чанках і **~2.07 ГБ на
    українському markdown** при `BATCH_SIZE=16`. Памʼять цього проєкту здебільшого
    українська — орієнтуватись треба на **верхню** межу.
  * Цифри — **Windows working set**. Історичні 5407 МБ — майже напевно Linux RSS і
    **не відтворені**; не переносити їх на поточну поведінку.
  * Пік **не** приписувати стелі потоків: контрольований A/B 9 проти 4 потоків дає
    різницю **1.0 МБ**. Це виміряно, і це спростовує попереднє припущення.
  * Пул `N` резидентів **не реалізовано** (NFR-5), тож множника `N×` немає.
  * ONNX-потоки/арена налаштовні. Модель тягнеться лише явним `warmup`, ніколи неявно.
- **NFR-10 · Надійність і мʼяка деградація.** Демон/бекенд недоступні → пошук деградує мʼяко
  (віддає що є + статус), а не падає; `reconcile-on-start` наздоганяє зміни, зроблені поки
  сервіс спав → **нічого не губиться**. **Деградація мусить бути чутною, а не тихою:**
  резидент може померти нижче Python (segfault в ONNX), тож він лишає нативний дамп у
  `~/.claude/mnemo/embed-crash.log` (`faulthandler`), а клієнт відрізняє «помер посеред
  запиту» (поломка — каже про неї) від «недосяжний» (звичайний фолбек). Мовчазний перехід
  на in-process модель — друга копія ~2.2 ГБ і ~50× повільніше — більше не допускається.
- **NFR-11 · Портативність.** Linux / macOS / Windows парність: один код, різниться лише
  інсталятор і спосіб автозапуску.
- **NFR-12 · Без важкої інфри.** Нативно, без Docker у v1; джерело правди — `.md` на місці
  (git або просто файли); індекс — одноразовий, gitignored, повністю відтворюваний з `.md`.

## Критерії приймання (звідки знаємо, що готово)

- Підключив банк → за деякий час пошук по ньому працює, **без жодного вікна** й без
  зависання сесії.
- Правка `.md` → watcher сам переіндексував; свіже видно в пошуку; масовий білд іншого
  банку цьому не заважав.
- Пошук під час індексації → миттєва відповідь зі статусом, а не блок.
- `mnemo service status` → видно, що живе; `stop`/`start` — керує тихо.
- Перезавантаження машини → сервіс піднявся сам (autostart), нічого не втрачено.
- Логи старші за `MNEMO_LOG_RETENTION_DAYS` → зникли; UI фільтрує за банком/часом.
- Той самий проєкт у Linux і Windows → однакова поведінка; різниця лише в інсталі.
- Кабінет каже «доступна нова версія» → клік → застосування, стара версія відповідає
  весь час стейджингу → якщо новий білд не пройшов health-check, автоматичний відкат
  на попередню версію, і сервіс лишається живим.
- `curl /mcp-tools/search?...` віддає **той самий текст**, що агент бачить через
  MCP; у Swagger видно рівно три ці ендпоінти й **жодного** `/api`.
- `mnemo init` у чистому проєкті → у `settings.json` **немає жодного хука**; правило
  `.claude/rules/mnemo-memory.md` описує канонічну розкладку памʼяті, і його ядро
  читається як самодостатня інструкція без згадок Claude Code.
