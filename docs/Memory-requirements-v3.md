# mnemo v3 — вимоги (functional + non-functional)

> **Третій документ трійки:**
> - `Memory-design-v3.md` — *що і чому* (архітектура, джерело правди рішень);
> - `Memory-requirements-v3.md` — *що система мусить робити* (FR) і *як мусить
>   поводитись* (NFR) — цей файл;
> - `Memory-implementation-v3.md` — *як і в якому порядку* (стек, блоки, фази).
>
> Вимоги — це критерії приймання: реалізацію звіряємо з цим списком.

---

## FR — функціональні вимоги (що система робить)

- **FR-1 · Банки.** Реєструвати довільні кореневі теки будь-де на диску; багато
  незалежних банків; реєстр — людиночитний JSON; кожен банк має власний індекс.
- **FR-2 · Індексація.** `.md → чанки(за заголовками) → вектори → sqlite-vec + FTS`;
  hash-diff (лише змінене), prune (видалене зникає), per-batch commit, батч ~16 чанків.
- **FR-3 · Пошук.** vector + FTS + RRF + фільтр скоупу; повертає релевантні секції;
  **ніколи не блокує**; до відповіді додає статус `indexing` / `empty` / `ready`
  (`empty` = бази немає ≠ «нема збігів»).
- **FR-4 · Автостеження + черга.** Watcher сам помічає зміни банків і ставить у чергу;
  пріоритет: поодинокі правки > масовий реіндекс (прапорець, типово ввімк.); робота — у фоні.
- **FR-5 · Обличчя.** MCP (search / tree / reindex) — по HTTP; CLI — клієнт сервісу;
  Web UI; опційний auto-inject хук. `memory_write` **не робимо** — правки лише нативними
  файловими інструментами.
- **FR-6 · Логи.** Події `query` (запит → повернуті чанки) і `index` (файл/масовий реіндекс)
  у SQLite `service.db`; читання з фільтром за банком і часом.
- **FR-7 · Web UI (v1).** Список банків, дерево файлів, перегляд `.md`, **chunk-viz
  лініями-роздільниками**, кнопки реіндексу (повний / по файлу), журнал; **без редагування** у v1.
- **FR-8 · Провайдери ембедингу.** `local` (e5-large, за замовчуванням); опційний `api`;
  per-service або per-bank; зміна провайдера → повна перебудова індексу банку.
- **FR-9 · Керування сервісом.** Команди `mnemo service start | stop | status | restart` —
  іменовані процеси, видимий стан (PID / порт / банки / черга).

## NFR — нефункціональні вимоги (як система поводиться)

- **NFR-1 · Тихі процеси, без вікон.** Жодного блимання консолі. Демони й будь-які
  спавни — windowless: Windows `CREATE_NO_WINDOW` / `pythonw`; Linux — відчеплені
  (`start_new_session`, stdio→devnull) / systemd.
- **NFR-2 · Мінімум спавнів.** MCP — по **HTTP** (Claude Code конектиться до URL, процес
  не запускається). Лишається тільки опційний хук — тонкий windowless HTTP-relay.
- **NFR-3 · Always-on + керованість.** Сервіс автозапускається і працює у фоні навіть без
  активної сесії; іменований; повний контроль `start/stop/status/restart`. On-demand — fallback.
- **NFR-4 · Неблокування.** Жодне обличчя чи хук не вішає сесію; пошук — миттєвий;
  індексація — завжди у фоні, без дедлайну.
- **NFR-5 · Продуктивність ембедингу.** Throughput обмежений CPU (стеля). Потоки демону
  `cpu*3//4` (override `MNEMO_EMBED_THREADS`); опційний пул воркерів (default 1) — для
  конкурентності, не множення throughput. Реальні цифри — заміряти, не обіцяти.
- **NFR-6 · Встановлення й автозапуск per-OS.**
  - *Linux:* `systemd --user` unit (`systemctl --user start/stop/status`), `loginctl
    enable-linger` для always-on; alias/PATH для CLI.
  - *Windows:* реєстрація `mnemo` у **PowerShell-профілі**; **Task Scheduler** (прихований)
    для автозапуску при вході; windowless-лаунчер демонів/хуків.
  - Без WSL, без Docker, без PowerShell 7, без зміни системного PATH.
- **NFR-7 · Безпека.** Усе на loopback за замовчуванням; API під токеном (як `embed.token`);
  Web UI лише локально. Вихід назовні (`api`-провайдер) — свідомий opt-in.
- **NFR-8 · Retention логів.** Логи обмежені за часом: env `MNEMO_LOG_RETENTION_DAYS`
  (типово 30 ≈ місяць); авто-prune старіших на старті + періодично; опційний backstop за рядками.
- **NFR-9 · Ресурси.** Одна копія локальної моделі в RAM (~1.6 ГБ) на машину; пул `N` → `N×`;
  ONNX-потоки/арена налаштовні. Модель тягнеться лише явним `warmup`, ніколи неявно.
- **NFR-10 · Надійність і мʼяка деградація.** Демон/бекенд недоступні → пошук деградує мʼяко
  (віддає що є + статус), а не падає; `reconcile-on-start` наздоганяє зміни, зроблені поки
  сервіс спав → **нічого не губиться**.
- **NFR-11 · Портативність.** Linux / macOS / Windows парність: один код, різниться лише
  інсталятор і спосіб автозапуску.
- **NFR-12 · Без важкої інфри.** Нативно, без Docker у v1; джерело правди — `.md` на місці
  (git або просто файли); індекс — одноразовий, gitignored, повністю відтворюваний з `.md`.

## Критерії приймання (звідки знаємо, що готово)

- Підключив банк → за деякий час пошук по ньому працює, **без жодного вікна** й без
  зависання сесії.
- Правка `.md` → watcher сам переіндексував; свіже видно в пошуку; масовий білд іншого
  банку цьому не заважав.
- Пошук під час індексації → миттєва відповідь зі статусом, а не блок.
- `mnemo service status` → видно, що живе; `stop`/`start` — керує тихо.
- Перезавантаження машини → сервіс піднявся сам (autostart), нічого не втрачено.
- Логи старші за `MNEMO_LOG_RETENTION_DAYS` → зникли; UI фільтрує за банком/часом.
- Той самий проєкт у Linux і Windows → однакова поведінка; різниця лише в інсталі.
